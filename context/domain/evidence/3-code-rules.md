## Soft and client-only rules

The paths below bypass a check. Each needs only the user's own session unless it says otherwise.

## Writers that work against a guard

Direct database API and RPC calls (W8) need the project URL and the publishable key. This code keeps both in server env only (`src/lib/supabase.ts:3`), so whether a user can make such calls in production is **unknown**. The repository's own database checks make exactly these calls with a user's session and that key, which shows what such a caller could do.

1. **`report_shop_block` is executable by every signed-in user** (`20260926112205_polite_shop_access.sql:129-130`).
   - A direct call stops or pauses any shop for the whole deployment. The test does exactly that as an ordinary user (`scripts/check-shop-gate-db.mjs:148-190`).
   - This works against the gate's rule of stopping only after a real 403 or challenge (`src/lib/services/shop-gate.ts:139-153`).
   - Re-enabling has no in-app path (`…polite_shop_access.sql:37`).
2. **`reserve_shop_request` is executable by every signed-in user** (`…polite_shop_access.sql:126-127`).
   - One user can take every slot of a shop's cap: one test user takes all 30 (`scripts/check-shop-gate-db.mjs:86-103`).
   - That blocks everyone's lookups and refreshes for that minute.
   - The cap counts reservations per shop, not per user (`…polite_shop_access.sql:76-79`).
3. **Self-service watching opens any shop item's shared prices.**
   - Any user can become a watcher of any format-valid shop item id: add it as a product (W1/W8), or confirm or insert a match to it (W3/W8).
   - From then on they read its observations and add their own (`…price_observations.sql:89-127`). Test: once user B adds X, B reads A's observations (`scripts/check-prices-db.mjs:305-312`).
   - A watcher's direct insert can add a plausible fake price, or a `missing` row, that every co-watcher then sees as the item's latest check (`…price_observations.sql:109-127`, `:137-138`; test inserts at `scripts/check-prices-db.mjs:213-235`).
   - This works against F5 ("missing" only on a clean answer) and G1 (which price is named cheapest), and it steers co-watchers' history low (H).
   - The migration comment records the fake price and the visible check times as accepted risks (`…price_observations.sql:85-86`); that is intent, not a guard.
4. **An owner can rewrite their own decision in any way the shape checks allow.**
   - Possible writes: back to "not found", from "not found" to a user match, or marking a match `auto`. The policy allows any state (`…removal_and_repin.sql:26-29`), and `state` and `decided_by` are in the update grant (`…price_observations.sql:28-31`). Test: the owner turns "not found" into a match directly (`scripts/check-matches-db.mjs:294-314`).
   - This works against D5's compare-and-swap and E's rule that only the lookup marks a match `auto`. It affects only the owner's own list.
5. **`watchlist_items` has a table-wide insert grant** (`…watchlist_items.sql:42`), so a direct insert can set `created_at`. The column has only a default (`:20`), and no later migration narrows the insert grant.
   - The good-price rule reads that time as the product's "added at" (`src/pages/watchlist/[id].astro:249`; `src/lib/services/watchlist.ts:215`; `src/lib/services/price-comparison.ts:477`).
   - So a backdated row can satisfy the 30-day condition at once (inference; no test found either way). It affects only the owner's judgement.
6. **The decision form stores a decision in the product's own shop**, which every read then ignores (D, `src/lib/services/matches.ts:67-79`).
7. **Crafted "Dodaj" posts carry the product's EANs, size, brand and caption from the client** (`src/components/watchlist/SearchResults.astro:68-79`). The server checks formats and hosts only (`src/lib/services/watchlist.ts:48-64`), so the user's own lookups are driven by data the shop never showed. This affects only the owner.
