## Recommendation

**Deploy on Cloudflare Workers** (a Worker with static assets, which is what the scaffolded `wrangler.jsonc` already describes; the tech-stack hand-off's `cloudflare-pages` should be read as this target, since Cloudflare now says "start new projects with Workers" and the Astro adapter dropped Pages in v13).

The project is already wired for it: `@astrojs/cloudflare` 14.3 is GA for Astro 7, `astro dev` runs on the workerd runtime through the Cloudflare Vite plugin, and wrangler 4 covers deploy, versions, rollback, secrets and log tailing from the terminal. It scores Pass on all five agent-friendly criteria, costs $0 to $5 a month at this traffic, and ships cron, previews, `llms.txt` docs and official MCP servers. The interview removed every reason to move: the app is stateless request/response (no persistent-process filter), users sit in one region (Poland, served from the nearest EU colo), the database stays on Supabase (no co-location weight), and there was no cost, DX or familiarity preference to break a tie. Vercel scored equally on the criteria but would require an adapter swap for no operational gain; the three-week timeline makes the already-working platform the conscious choice, with the cross-check risks below carried into the register.

All statuses were checked on 2026-09-20.

**Cloudflare Workers.** `@astrojs/cloudflare` 14.3 (GA) peers on Astro ^7.2 and wrangler ^4.125 and depends on `@cloudflare/vite-plugin` (installed 1.54.8), so `astro dev` and `astro preview` run in workerd with no separate `wrangler dev`. Deploy is `wrangler deploy`; staged rollout is `versions upload` then `versions deploy`; `wrangler rollback` reaches the last 100 versions; `wrangler tail --format json --status error` streams logs; CI authenticates with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Previews come from Workers Builds (GitHub integration, GA date unverified) as `<version>-<worker>.<subdomain>.workers.dev` URLs, protectable with Cloudflare Access "Previews only" (2026-08-14), but disabled when the Worker exports a Durable Object. Docs: `developers.cloudflare.com/llms.txt`, any page plus `/index.md`, source on GitHub. Free plan: 100k requests/day, 10 ms CPU per invocation, 50 subrequests per request; Paid $5/month: 10M requests, 30 s CPU, 10,000 subrequests. Cron Triggers exist on Free (5 per account, same CPU cap). Rate Limiting binding is GA but counts per colo; KV, D1 and Durable Objects have free tiers. MCP servers (`mcp.cloudflare.com`, docs, builds, observability, bindings) and a skills repo exist without status labels. Estimated cost: $0 only if every SSR response stays under 10 ms CPU, otherwise $5 flat at both 10k and 100k requests.

**Vercel.** `@astrojs/vercel` 11 (GA) runs SSR as Node functions on Fluid compute (GA, Node 24 default); the whole-app Edge runtime was removed. CLI: `vercel` (preview), `vercel --prod`, `vercel rollback` (Hobby: only to the previous production deployment), `vercel promote`, `vercel logs --follow` (5-minute stream, one-hour retention on Hobby). Every branch gets a preview URL with Vercel Authentication on by default. Docs: `vercel.com/llms.txt` and `.md` suffix. Hobby is free but non-commercial only, single region (fra1 settable, not tested), 1M invocations and 4 CPU-hours a month, and overage pauses the project for 30 days; Hobby cannot deploy private repos owned by a GitHub organization. Cron is GA on all plans with a once-per-day minimum on Hobby, which matches FR-015. WebSockets are beta. Vercel KV and Postgres were sunset; Upstash Redis via Marketplace is the cheap counter. MCP at `mcp.vercel.com` is beta with deploy and log tools. Egress IPs are dynamic AWS ranges; static IPs are Pro-only at $100/month. Estimated cost: $0 at both volumes.

**Render.** Native Node runtime (Node 24 default, 22 supported) with an official Astro guide using `@astrojs/node`; build `npm run build`, start `node dist/server/entry.mjs`, `HOST=0.0.0.0`. CLI v2.28: `render deploys create <id> --wait --confirm -o json`, `render logs -r <id> --tail`; rollback only via dashboard or `POST /services/{id}/rollback`; Blueprints (`render.yaml`) are GA. Per-service PR previews are GA on all plans; Blueprint preview environments need Pro ($25). Docs: `render.com/docs/llms.txt`, `.md` suffix, skills repo. Hobby workspace is $0 with a Free instance (0.1 CPU, 512 MB) that sleeps after 15 idle minutes and wakes in about a minute; Starter is $7/month; cron jobs cost at least $1/month; Postgres Free expires after 30 days. Key Value (Valkey) free tier serves a counter. Hosted MCP at `mcp.render.com/mcp` is GA. Frankfurt is available for every service type; outbound IPs are fixed shared ranges, dedicated IPs Pro-only at $100/month. Estimated cost: $0 on Free (with sleep) or about $8/month on Starter plus cron, identical at both volumes.

**Netlify.** `@astrojs/netlify` 8.2 (GA, Astro 7 day one) runs SSR as a Node Function on Lambda. CLI: `netlify deploy` (draft), `netlify deploy --prod`, `netlify logs --follow --function <name>`; no rollback command, but `netlify api restoreSiteDeploy` calls the restore endpoint. Deploy Previews are GA and free, with password or private visibility on the Free plan. Docs: `docs.netlify.com/llms.txt`, `.md` suffix. Pricing is credit-based since 2025-09-04: Free has 300 credits and pauses every site when spent; a production deploy costs 15 credits, so roughly eleven deploys a month exhaust Free before traffic does; Personal is $9/month. Scheduled Functions are GA on all plans (30 s limit). Functions default to Ohio; EU regions (fra) require Pro ($20/month), so on Free every Polish page view crosses the Atlantic to reach the shop APIs and back. Blobs are GA but Netlify's own guidance says not to build counters on them. MCP (`@netlify/mcp`) is unlabeled. Estimated cost: Free only with very few deploys, otherwise $9 to $14/month.

**Fly.io.** `fly launch` detects Astro and generates a Dockerfile for `@astrojs/node`; the default launch is two 1 GB machines, so pass `--ha=false --vm-memory 256`. CLI: `fly deploy`, `fly logs`; rollback is `fly deploy --image <previous image>` (config and secrets are not reverted); CI uses a deploy token. No built-in previews; the `fly-pr-review-apps` action creates an app per PR. Docs have no `llms.txt` but the source is public markdown on GitHub. No free tier since 2024-10-07 (trial only); a shared-cpu-1x 256 MB machine in Amsterdam costs about $2/month, a static egress IP $3.60/month. WebSockets and persistent processes are native; Scheduled Machines are GA but imprecise. Managed Postgres v2 is beta and region-limited; Upstash Redis is GA. `fly mcp` is experimental. Warsaw (waw) was deprecated in the September 2025 region consolidation; fra, ams, arn, cdg and lhr remain. Cold start is about 2 s from stop, 100 to 250 ms from suspend. Estimated cost: $2 to $3/month at both volumes, plus $3.60 for a fixed egress IP if needed.

**Railway.** Railpack (GA) builds Node 22/24 without a Dockerfile; an SSR Astro app needs an explicit `start` script (`node ./dist/server/entry.mjs`) and must bind `0.0.0.0` on the injected `PORT`; Railway's own Astro guide still cites the removed `hybrid` output. CLI: `railway up --ci`, `railway redeploy`, `railway logs`; rolling back to an older deployment is dashboard-only with a 72-hour window on Hobby. PR environments are GA. Docs: `docs.railway.com/llms.txt`, `.md` suffix, GitHub source. Hobby is $5/month including $5 of usage; Free gives $1 credit and no custom domain; unverified GitHub accounts get a limited trial with restricted outbound network, which would block the shop API calls. Cron schedules are GA with a five-minute minimum and must run as a separate service. Postgres and Redis are unmanaged templates. Hosted MCP (`mcp.railway.com`) is GA and bundled in the CLI. Amsterdam is selectable on all plans; static egress IPs are Pro-only. Estimated cost: $5/month at both volumes.

### Shortlisted Platforms

#### 1. Cloudflare Workers (Recommended)

It won on fit and momentum rather than on criteria alone: the adapter, wrangler config, workerd dev server, README and CI skeleton from the starter all target it, so the first deploy is `npm run build && npx wrangler deploy` rather than an adapter migration. On the criteria it is the only platform with terminal-driven staged deploys and hundred-version rollback, agent docs in three formats, and first-party MCP servers plus agent skills. Cron on the free plan covers the post-MVP daily refresh, and the EU colo nearest a Polish shopper serves the app. Its real costs are the ones the cross-check lists: a 10 ms CPU cap on the free plan, a per-colo rate limiter, the Durable-Object-versus-preview conflict, and shared egress IPs.

#### 2. Vercel

Equal on the criteria and free for a non-commercial personal project, with protected previews on by default, a settable EU region, and a once-daily cron that maps exactly onto FR-015. The gap is operational rather than technical: switching to `@astrojs/vercel` and Node functions costs a day of the three-week budget, Hobby rollback only reaches one deployment back, runtime logs vanish after an hour, and the Hobby plan cannot deploy org-owned private repos. Egress is dynamic AWS IPs, so it does not solve the shared-IP question either. It is the fallback if Workers' CPU cap or workerd incompatibilities bite.

#### 3. Render

A conventional Node server in Frankfurt with a GA hosted MCP server, PR previews on every plan, Blueprints as infrastructure-as-code and a clean `llms.txt`. It ranks third because the free instance sleeps after 15 idle minutes and takes about a minute to wake, which fails the "usable at the shelf" requirement, so the honest price is about $8/month; rollback is API-only; and the Node adapter plus start-command conventions replace the starter's Cloudflare wiring. Fly.io is noted as the specific escape hatch if shop APIs reject cloud egress, because it is the only shortlist-adjacent option with a cheap fixed egress IP.

## Anti-Bias Cross-Check: Cloudflare Workers

### Devil's Advocate — Weaknesses

1. The free plan caps CPU at 10 ms per invocation. React 19 SSR of a product page plus five parallel shop fetches and JSON parsing will cross that line intermittently, surfacing as error 1102 that looks like a shop failure. The realistic floor is Workers Paid at $5/month with a 30 s CPU budget.
2. The Rate Limiting binding counts per colo and is eventually consistent, so it cannot enforce the PRD's deployment-wide per-shop cap. The correct Cloudflare primitive is a Durable Object, and a Worker that exports one loses preview URLs. The cap and the preview workflow conflict unless the counter lives elsewhere, for example an atomic row in Supabase.
3. Every outbound fetch leaves from shared Cloudflare edge IPs that vary by colo and carries a `CF-Worker` header. Whether the five chains treat that traffic like the plain curl probes in `docs/research/polish-drugstore-price-apis.md` is unverified, and no fixed egress IP exists below Enterprise. If a shop blocks it, the fix is a proxy on another platform.
4. workerd with `nodejs_compat` is not Node. Adapters that read dynamic values from shop pages (Super-Pharm's search key, the Luigi's Box tracker ids) cannot use jsdom-style libraries, and a package that breaks only at runtime is found only by running in workerd. The 2026 issue tracker also reports adapter 14 dev-server crashes from an optimizeDeps race.
5. Per-request limits bite a fan-out design: 6 simultaneous outbound connections per request, redirects count as subrequests, and the middleware already spends one network round trip on Supabase `getUser()` for every request.

### Pre-Mortem — How This Could Fail

The team shipped Drogeria Radar on Cloudflare Workers and stayed on the free plan because traffic was tiny. Once the good-price history query joined the five-shop fan-out, product pages began failing with error 1102 at random. The failures looked like shop outages, so evenings went into adapter debugging before anyone looked at CPU time. Upgrading to Workers Paid fixed that, but the per-shop request cap had been built on the Rate Limiting binding, whose per-colo counters never enforced a deployment-wide limit. Two users in different cities tripped Hebe's threshold in the same minute, and Luigi's Box started returning empty results to requests carrying the `CF-Worker` header. The fix was a Durable Object counter, which silently switched off preview URLs and broke the review loop for every pull request. Meanwhile the daily refresh, added as a Cron Trigger, needed a custom entrypoint nobody had planned for, and the HTML-parsing library that read Super-Pharm's search key only worked in Node. Six months in, the fetch layer lived on a separate Fly machine, the site on Workers, and the two platforms disagreed about secrets.

### Unknown Unknowns

- Preview URLs are public by default at `<version>-<worker>.<subdomain>.workers.dev`. For an invite-only app they must sit behind Cloudflare Access ("Previews only", which needs Zero Trust enabled on the account) or be disabled, and previews must never point at the production Supabase project.
- Cron Triggers need a custom entrypoint that exports `scheduled` and calls `handle()` from `@astrojs/cloudflare/handler`, so adding FR-015 means changing `main` in `wrangler.jsonc`; on the free plan the scheduled run gets the same 10 ms CPU budget and runs on "underutilized machines" in any region.
- `wrangler deploy` deletes plain `vars` absent from the config file unless `--keep-vars` is passed; secrets set with `wrangler secret put` survive. Keep configuration in `wrangler.jsonc`, secrets only via the CLI, nothing defined in the dashboard.
- The hand-off says `cloudflare-pages`, but the scaffold targets Workers with static assets; the Vite plugin, cron, rate limiting and Workers Logs are Workers-only, `astro dev` already runs in workerd, and `wrangler dev` or `wrangler pages` are the legacy path for this project. With a `compatibility_date` of 2026-08-04 or later `nodejs_compat` becomes the default; the scaffold pins 2026-05-08 with the flag explicit, so bump the date deliberately, not casually.
- Placement follows the visitor's nearest colo and Smart Placement is beta, so EU-only execution is not guaranteed without Enterprise Regional Services; `wrangler tail` is live-only and Workers Logs retention is short, so evidence of an intermittent failure must be captured while it happens.

## Operational Story

- **Preview deploys**: connect the GitHub repo to Workers Builds with `main` as the production branch; every push to another branch runs `wrangler versions upload` and posts a `<version>-<worker>.<subdomain>.workers.dev` URL plus a stable branch alias on the PR. Before enabling it, turn on Cloudflare Access for the Worker with the "Previews only" policy so the invite-only app is not publicly reachable; previews produce no logs, disappear if the Worker ever exports a Durable Object, and must use a non-production Supabase project. Whether fork PRs are built was not covered by the research. The first deploy (2026-09-23, `context/deployment/deploy-plan.md`) keeps previews off, with `preview_urls` false and Preview Builds unchecked, because versions of the same Worker inherit production secrets. Since 2026-09-22 branch builds run `wrangler preview` (Worker Previews) instead of `versions upload`.
- **Secrets**: `SUPABASE_URL` and `SUPABASE_KEY` live as Worker secrets (`npx wrangler secret put SUPABASE_URL`, then the same for `SUPABASE_KEY`), encrypted and readable only by the Worker at runtime through `astro:env/server`; locally they live in the gitignored `.dev.vars` and `.env`. CI holds `CLOUDFLARE_API_TOKEN` (the "Edit Cloudflare Workers" template) and `CLOUDFLARE_ACCOUNT_ID` in GitHub Secrets. Rotation is a new `wrangler secret put` after rotating the key in the Supabase dashboard; `wrangler deploy` never touches secrets.
- **Rollback**: `npx wrangler versions list`, then `npx wrangler rollback <version-id> --message "<why>"` (or plain `npx wrangler rollback` for the previous version); it completes in seconds and reaches the last 100 versions, but is refused if a Durable Object class changed. Supabase migrations do not roll back with it, so write migrations expand-then-contract and never drop a column in the same release that stops writing it.
- **Approval**: a human runs production deploys (`wrangler deploy` or a merge to `main` once auto-deploy exists), production `wrangler secret put`, Supabase migrations against the production project, deletion of KV/D1/Durable Object storage, and `compatibility_date` bumps. An agent may run unattended: `wrangler deploy --dry-run`, `wrangler versions upload` (preview only), `wrangler versions list`, `wrangler deployments list`, `wrangler tail`, `npm run build`, `npm run lint`, `npx astro check` and `npm run smoke` against a preview URL.
- **Logs**: live runtime logs with `npx wrangler tail --format json --status error` (or `--format pretty`, `--search <text>`); stored logs in Workers Logs, enabled by `observability.enabled` in `wrangler.jsonc`, readable in the dashboard or through Cloudflare's observability MCP server (`observability.mcp.cloudflare.com/mcp`); build logs in the Workers Builds dashboard or the builds MCP server; CI logs in GitHub Actions (`gh` 2.101 is installed; the agent needs `gh auth login` before it can read runs).

## Getting Started

Validated against the versions installed in this repository: astro 7.3.2, `@astrojs/cloudflare` 14.3.1, `@cloudflare/vite-plugin` 1.54.8, wrangler 4.131.1, Node 24.12 locally.

1. Authenticate and name the Worker: `npx wrangler login`, then `npx wrangler whoami`; change `name` in `wrangler.jsonc` (and `package.json`) from `10x-astro-starter` to `drogeria-radar`. Leave `main`, `assets` and `compatibility_date` as scaffolded.
2. Local development: `cp .env.example .dev.vars` and `cp .env.example .env`, fill in the Supabase values, then `npm run dev`. The dev server already runs in workerd via the Vite plugin; do not add `wrangler dev` or `wrangler pages dev`.
3. Production secrets: `npx wrangler secret put SUPABASE_URL` and `npx wrangler secret put SUPABASE_KEY` (each prompts for the value). Nothing else goes in the dashboard.
4. First deploy: `npm run build && npx wrangler deploy --dry-run` to check the bundle, then `npm run build && npx wrangler deploy`; it prints `https://drogeria-radar.<subdomain>.workers.dev`. Verify with `npx wrangler tail --format pretty` in one terminal and `BASE_URL=https://drogeria-radar.<subdomain>.workers.dev npm run smoke` in another (needs a reachable Supabase with email confirmation off).
5. Egress probe before adapter work: add a temporary route under `src/pages/api/` that fetches each of the five shop search endpoints from the research note and returns their HTTP status codes, ship it as a preview with `npm run build && npx wrangler versions upload`, call the preview URL, record the outcome in `docs/research/polish-drugstore-price-apis.md`, then delete the route. Only after that, connect the repo to Workers Builds (production branch `main`) with Cloudflare Access "Previews only" enabled. The first deploy ran this probe on a throwaway Worker outside the repo instead, and connected Workers Builds with preview builds off (`context/deployment/deploy-plan.md`).

## Out of Scope

The following were not evaluated in this research:

- Docker image configuration
- CI/CD pipeline setup (the scaffolded `.github/workflows/ci.yml` lints, checks and builds but does not deploy; `cloudflare/wrangler-action@v4` is the documented step when that is added)
- Production-scale architecture (multi-region, HA, DR)
