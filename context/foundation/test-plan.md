## 1. Strategy

Tests follow three non-negotiable principles for this project:

1. **Cost × signal.** The cheapest test that gives a real signal for the risk wins. Do not promote to e2e because e2e "feels safer." Do not put a vision model on top of a deterministic visual diff that already catches the regression.
2. **User concerns are first-class evidence.** Risks anchored in "the owner is worried that a stale price looks current, and the failure would surface somewhere in the price display" carry the same weight as PRD lines or hot-spot data.
3. **Risks are scenarios, not code locations.** This plan documents _what could fail_ and _why we believe it's likely_ — drawn from documents, interview, and codebase _signal_ (churn, structure, test base). It does NOT claim to know which line owns the failure. That knowledge is produced by `/10x-research` during each rollout phase. If the plan and research disagree about where the failure lives, research is the ground truth.

Hot-spot scope used for likelihood weighting: `src/` (without `src/lib/services/shops/fixtures/` and `src/dev/`), `supabase/migrations/`, `scripts/`. The project started on 2026-09-20, so the 30-day window is its whole history: 36 commits in scope.

## 6. Cookbook Patterns

How to add new tests in this project. Each sub-section is filled in once the relevant rollout phase ships; before that, the sub-section reads "TBD — see §3 Phase <N>."

### 6.1 Adding a unit test

- **Location**: beside the module, as `<module>.test.ts` under `src/`; Vitest includes `src/**/*.test.ts` only.
- **Shop answers**: only through `createReplayFetch` (`src/lib/services/testing/replay-fetch.ts`) with recordings in `src/lib/services/shops/fixtures/`. Assert which URLs the replay served, because a miss looks like `failed/network`.
- **A component's markup**: a component that keeps no state renders in Node with `renderToStaticMarkup` (`react-dom/server`), with `createElement` in place of JSX, which a `.test.ts` can't hold, and needs no DOM or new dependency. Build its props as the view does, such as an island's rows through its reducer from the rows in `src/lib/services/testing/island-shops.ts`. Reference: `src/components/watchlist/ShopCard.test.ts`, which pins a line e2e can't reach.
- **Reference test**: `src/lib/services/shop-matching.test.ts`.
- **Run locally**: `npm run test`; one test with `npx vitest run <file> -t "<name>"`.

### 6.2 Adding an integration test: stubbed reads, routes, the local database and two users

- **Pick the pattern by what the risk needs** (cost × signal):
  - a decision resting on stored rows, a page's wiring included → a stubbed read (1);
  - what a route asks a shop → the route's handler through the real gate (2);
  - what the database does with a write → a database test (3);
  - what another user gets through the app → the two-user check (4);
  - a new table, view or function → the catalogue check (5).
- **1. Stubbed reads** (`src/lib/services/price-pages.test.ts`):
  - `stubSupabase({ relations, rpc })` (`src/lib/services/testing/stub-supabase.ts`) answers each relation and RPC by name, applies a query's filters to its canned rows and records every query. A name it wasn't given answers an error, so a forgotten read never reads as empty.
  - Use it for a row the database would refuse, such as an odd price row, which only a stub can serve.
  - Move a page's decision into a service first ("Keep decision logic in tested services"), since no test renders a page.
  - The seam table serves one stored state to both pages' own reads and wiring, the product page's through `openProductPage`, the page's own call, on a product loaded as the page loads it (`loadWatchedProduct`), one fault at a time. Its expected values come from the PRD's guardrail, US-01 and the owner's calls, never from the rule under test. Its negative control: no RPC is called, so no shop was asked.
- **2. A route's handler through the real gate** (`src/lib/services/price-routes.test.ts`):
  - Import the route's exported handler (`POST`) and call it with a context of `request`, `url`, `locals` (a stand-in client and no user) and `redirect`. Astro builds every file under `src/pages/` as a route, so the test lives under `src/lib/services/`.
  - The gate is the real one, over the stand-in's `reserve_shop_request` and `report_shop_block`. The shop answers come from `createReplayFetch`, stubbed in as the global `fetch` (`vi.stubGlobal`).
  - `world` sets both up, and `served`, `bodiesSentTo` and `reservations` read what the shops were sent and what the gate reserved (`src/lib/services/testing/gate-world.ts`), for every test that reaches a shop through the gate: the product page's own call (`openProductPage`, `src/lib/services/product-page.test.ts`) runs on the same world.
  - Assert the reservations and the served URLs, never only the status: none for each refusal, exactly the stated cost for each valid call, and nothing after a 403. A valid call serving its URLs is the negative control.
  - The served URLs count every request sent, one the replay doesn't know included, which reads as `failed/network`. So a call that needs every shop answered also asserts the route's outcome, such as a refresh's `done`, and a POST's body.
  - A handler test skips the middleware, Astro's origin check and the headers. Smoke and the two-user check (4) cover those on the preview.
  - The decision route's handler (`src/lib/services/match-routes.test.ts`) reaches no shop, so it runs the same context without the gate. It asserts the redirect and, for each of the guardian's refusals, that no decision was written. Both route files share the context and the app's origin (`src/lib/services/testing/route-context.ts`) and the stored rows (`stored-rows.ts`).
- **3. A database test** (`src/lib/services/matches.db.test.ts`):
  - Name it `<module>.db.test.ts` under `src/`.
  - `npm run test:db` (`vitest.db.config.ts`) runs it, in CI's `smoke` job against its local stack. The default run, which the end-of-turn hook and CI's `ci` job use, leaves it out, since neither has a database.
  - Refuse any `SUPABASE_URL` but the local stack before any request, and sign up a fresh throwaway user through Auth. Never a secret key.
  - Import the real service function, never a hand copy of its query, which drifts.
  - Its negative control shows the database alone would let the wrong write through: an update by id over a changed decision succeeds.
  - Run locally with `npx supabase start`, then `SUPABASE_URL=http://127.0.0.1:54321 SUPABASE_KEY=<anon key> npm run test:db`.
- **4. Two users over HTTP** (`scripts/check-two-users.mjs`):
  - Against the workerd preview, user B gets for user A's product exactly what a product no one has gets: the same status, the same body, or the same `Location` once the id is swapped. Every answer is `private, no-store`.
  - A new route or page that takes a product's id joins its list.
  - A is seeded through supabase-js after an Auth sign-up. B signs in through the app's Polish form.
  - A's product has a name of its own, which none of B's pages may show.
  - Every enabled shop is held for the run (`stopShops` and `restoreShops`, `scripts/e2e-local-db.mjs`), so a route that leaked would meet a stopped shop. It refuses to start while another run holds them, and checks that none is enabled before either user's requests.
  - **Negative control:** as A, the product page, the price route and the product's refresh answer differently from a missing id.
  - **Afterwards:** A's rows, read back before the requests, are unchanged, B's own are empty, and the request log's mark hasn't moved, which shows the hold lasted.
- **5. The catalogue check** (`scripts/check-catalog-db.mjs`):
  - As the local superuser, it holds `public` to a reviewed list of relations and functions, each with its protection:
    - RLS on every table;
    - `security_invoker` on every view;
    - no privilege of anon but EXECUTE on `applied_migrations()`;
    - nothing PUBLIC may execute.
  - A migration that adds one adds it to the list, in the same change.
  - Its self-test plants every fault in a transaction it rolls back, and each must be flagged before the real catalogue is read.
- **Done means:** the test goes red under a deliberate break of the behaviour it protects.
  - A check that needs the local stack can't be broken on a machine without Docker. It carries its own negative control, which CI runs, and its rules can be broken offline over canned rows or a stand-in app, as rollout Phase 2's were.
- **Run locally:** patterns 1 and 2 with `npm run test`. Patterns 3–5 need `npx supabase start`; the two-user check also needs the preview (`npm run build`, then `npm run preview`).

### 6.3 Adding an e2e test

- **Location and naming**: `tests/e2e/<risk-facet>.spec.ts`, one test per file, titled after its risk (`"#7: on a phone, …"`). A provenance header names the risk, the facet the test protects and the seed. A spec that judges prices also names where its expected values come from (the PRD and the decision records, never the code under test).

- **Seeding**: the helpers in `tests/e2e/support/watchlist-data.ts` act as the run user.
  - `addProduct({ source, name, productUrl })` adds a product from any priced shop, its own shop, with a fresh id in that shop's shape (`FRESH_IDS`, whose shapes `matchShop` below lists) and no picture, and checks that no earlier run's prices come with it. The match is automatic unless the story says the user picked it (`decidedBy: "user"`), and it has an item page (`productUrl`) only where a spec asserts "Zobacz w sklepie".

A check older than 24 hours needs `backdateChecks`, seeding's one superuser write (`scripts/e2e-local-db.mjs`).

- **Shops**: no spec reaches a shop.
  - The setup holds every enabled shop in the local `public.shops` under the run's name, refuses to start while another run or a manual `stop` holds them, and checks that every priced shop (`PRICED_SHOPS`) then answers `stopped`.

  - Assert inside `main`, since a phone keeps the list beside the product hidden in the page.
  - A spec without JavaScript sets `test.use({ javaScriptEnabled: false })`.

Drive it with `playwright-cli -s=projekt` after `state-load playwright/.auth/user.json`. Afterwards restore the shops (`… restore`) and stop the preview (`npx astro preview stop`).

### 6.4 Adding a test for a shop adapter

- **Location and naming**: the adapter is `src/lib/services/shops/<shop>.ts` and its test `<shop>.test.ts` beside it. Its recordings are `src/lib/services/shops/fixtures/<shop>-<case>.json`, such as `hebe-ean-online.json`. Rossmann's adapter, `rossmann.ts`, calls Rossmann's own REST API: one parse of its text search serves the list's products (`searchRossmann`) and a lookup's candidates, each with the offer its item's price fields give by the detail's rules (`searchRossmannItems`, its registry entry's `search`), and its prices come one product per request (`fetchRossmannPrices`). `rossmann.test.ts` beside it also pins its registry entry, since the registry has no test of its own. A shop on Luigi's Box maps only its own attributes onto the shared client (`luigis-box.ts`). Its test covers that mapping and the shop binding, while `natura.test.ts` pins the client's batching, refusal and missing-versus-failed rules.
- **Another search provider**: a shop whose search isn't Luigi's Box sends its own requests and reads its own answers, and its pinned prices follow the shared rules (`pinned-prices.ts`) with its own batch size, so its test covers those rules too. Super-Pharm's search is Algolia (`super-pharm.ts`): every search and price request is a POST to one URL, with the app id and the public search key in headers, and its pinned prices go 20 ids a request. Its recordings are `super-pharm-name-search.json` and `super-pharm-pinned-rules-off.json`, made with the adapter's own requests; `super-pharm-pinned.json`, made before its price requests switched Algolia's query rules off (`enableRules=false`); `super-pharm-name-search-one.json`, `super-pharm-search-empty.json` and `super-pharm-pinned-one.json`, the research probes' answers; the seven `super-pharm-lookup-<product>.json` (2026-10-06), each the name search a lookup sends for a recorded Rossmann product, kept whole; and `super-pharm-search-nivea-soft.json` and `super-pharm-search-aa-laab.json` (2026-10-06), the list's search for each recorded text, kept whole.
- **Recording a fixture**: a real answer, never an invented one, recorded only with the owner's OK.
  - From the developer machine, never from CI: `curl` with the gate's User-Agent (`DrogeriaRadar/0.1 (+https://github.com/yaroslavkhudchenko/10xcourseproject)`) and `Accept: application/json`, following no redirect.
  - An Algolia request is a POST with `Content-Type: application/json`, the app id and the key in `X-Algolia-Application-Id` and `X-Algolia-API-Key`, and the adapter's exact body. A recording's headers stay out of the repository.
  - One request at a time, at least 2 s apart, to the shop's API host only, never to a page whose robots.txt refuses AI crawlers.
  - Keep the answer as it came, cut at most to its first 5 hits, with no personal data: a person's e-mail address in a field the app never reads, as Natura's GPSR fields held one, reads `[email removed]` (`natura-search-aa-laab.json`). Keep every number as written: a plain `JSON.parse` and `JSON.stringify` round Luigi's Box's `identity_hash`, so trim with a reviver that keeps each number's source text (`JSON.rawJSON`).
  - The test's header names each fixture's request and date, as every adapter's test does.
- **The cases**:
  - the mapping on the recordings: every field a candidate or an offer carries, and each size as text that `parseSize` reads back as the same size;
  - the matching rule's outcomes (`pickMatch`) on the real candidates, against watched products taken from recordings wherever one exists, with the name and caption its name check reads. The products recorded on 2026-10-06 are Rossmann's searches `rossmann-search-nivea-soft.json`, `rossmann-search-aa-laab.json`, `rossmann-search-nivea-creme-soft-zel.json`, `rossmann-search-head-shoulders-classic-clean.json` and `rossmann-search-maybelline-lash-sensational.json`, which `super-pharm.test.ts` reads through Rossmann's own adapter. Against `natura-search-nivea-soft.json` and `hebe-search-aa-laab.json`, a product's EANs are hidden, so only the name check may accept an item. A product picked in another shop than Rossmann is one of that shop's recorded items as "Dodaj" stores it, without a caption, so every word of its name tells it apart. Rossmann's answers to three such products' lookups are `rossmann-lookup-nivea-soft-300.json`, `rossmann-lookup-aa-laab-150.json` and `rossmann-lookup-maybelline-sky-high-cosmic-black.json` (2026-10-08), each the search by name its lookup sends (`nameQuery`), 10 items a page, kept whole, which `shop-matching.test.ts` serves through the real gate;
  - the list's search across the shops (`product-search.test.ts`), on the eight recorded answers of 2026-10-06, each shop's search for "nivea soft" and for the AA LAAB face wash's name, 10 hits each, kept whole (`<shop>-search-nivea-soft.json`, `<shop>-search-aa-laab.json`): through the real gate, the four requests, one per shop, with Super-Pharm's POST body, every entry item by item, each join and each look-alike kept apart, each shop's line, „Na liście”, and what "Dodaj" adds, round-tripped through the add form's checks. What no recording holds goes on edited copies: an item two entries would take, and an item of a shop with EANs that the name rule accepts;
  - pinned batches: an id the shop answers without is `missing`, a hit nobody asked for leaves every unanswered id `failed`, never `missing`, one id more than a request holds makes 2 requests (51 on Luigi's Box, 21 on Super-Pharm), and a refusal stops the rest, as two failed requests in a row do too (`FAILED_REQUESTS_BEFORE_STOP`, which `price-refresh.test.ts` pins through a refresh);
  - the shop binding: every `gate.fetch` call and every reservation names the shop, and every URL carries its tracker; on Algolia, every request carries the app id and the key, and no log line holds the key.
- **Broken copies** (risk #5): each changes one thing in a deep copy of a recording (`structuredClone`), or puts a page where the JSON was.
  - The changes, on every adapter: a field removed, a string where a number belongs, HTML instead of JSON, an answer without its hits list, and an answer without hits whose own count doesn't say it matched none.
    - On Rossmann also its 404 without its `application/problem+json` media type, and an item that lost its `name`, which its generic `fallbackName` mustn't replace. On its item search also an item's price sent as text or missing, which costs the candidate only its offer and logs nothing, since an item without a price is still a product to add, and an availability that isn't text, which is counted (below).
    - On Luigi's Box also the 404 text/plain answer to an unknown tracker (`natura-unknown-tracker.json`, which names no shop), and a hit of another type, which counts as one that can't be read: only a hit of `type: "query"` is a query suggestion, the only other kind Luigi's Box was ever recorded sending.
    - On Algolia also a count of hits (`nbHits`) above the hits an answer holds, price text that doesn't read as a price, availability flags that aren't a 1 or a 0, and a 400, while a 403 stops the shop. The 403 is pinned with Algolia's documented error answer (`ALGOLIA_403` in `super-pharm.test.ts`), labelled as documented, never as recorded, since Super-Pharm's answer to a rejected key was never recorded.
  - Each gives `unavailable/failed`, or for an odd value costs only that value (below), with one log line (a 400's is the gate's), never a wrong price, "not found" or `missing`.
  - An answer without hits means nothing found only when its own count says it matched none, as every recorded empty answer does: Rossmann's `totalCount` 0, Luigi's Box's `total_hits` 0 with `next_page` null, and Algolia's `nbHits` 0 on `page` 0. Any other empty answer is a gap, logged as "unexpected empty answer".
  - Odd values cost only themselves: an availability that can't be read counts as not orderable, and a 30-day low or a regular price that can't be read is left out. Each is counted in a log line whose reason reads the same in every shop that logs it: "availability unread", "30-day low unread", "regular price unread". The lines give counts only, never a product; Rossmann's price check, one product per request, logs only its availability, with the value's kind, and its item search counts an availability among its items with an offer, as the batched shops count theirs.
  - Change a copy the way the shop could plausibly change, not towards what the parser already tolerates.
- **Refusals and failures** (risk #3): each goes through the real gate, with `reserve`, `reportBlock` and `gateLog` spies.
  - The refusals: a 403; a challenge (`cf-mitigated: challenge`, whatever its status); a 429 and a 503 with `Retry-After`; a capped, paused or stopped reservation.
  - The plain failures: a 500, a network error, a timeout through the gate's short `timeoutMs`, and an unreachable counter, which sends nothing and reads as a failure, not a refusal.
  - Assert the requests (or POST bodies) served, the reservations, the reported block and the gate's outcome, never the outcome alone.
  - The answers no recording holds and the readers of what a test got are defined once, in `src/lib/services/testing/shop-answers.ts`: `CHALLENGE`, `NOT_FOUND_PAGE`, `stallingFetch` (a 200 whose body never ends), `pauseSecondsOf`, `gateOutcomes` and `loggedLine(s)`.
- **Asserting the replay's URLs**: build a real gate (`createShopGate`) over `vi.fn(createReplayFetch(entries))` and assert every URL it served (`requestedUrls`). Spell each URL out in the test, with the tracker, the parameter order and the encoding, rather than building it with the adapter's code. A URL the replay doesn't know rejects, which the gate reports as `failed/network`, so a test that checks only the outcome can pass on the wrong request.
- **Asserting POST bodies**: an Algolia request goes to one URL whatever it asks, so a recording names the body it answers (`requestBody`), and the replay serves it only for exactly that text. Spell each body out in the test too, with the parameter order and the form encoding (a space as `+`), and assert every body the replay served beside its URL, with the app id and key headers on every request (`sentRequests` in `super-pharm.test.ts`). A test also pins the spelled-out bodies against the ones the recordings were sent with.
- **Done means**: a deliberate break of each rule the adapter adds turns a named test red, such as offering an item the shop doesn't sell online, pricing from the regular price during a sale, reading the size from the wrong attribute, or counting an item sold only in the shops as orderable.
- **Reference tests**: `src/lib/services/shops/rossmann.test.ts` for Rossmann's own API, one product per price request, and its registry entry; `src/lib/services/shops/hebe.test.ts` and `src/lib/services/shops/natura.test.ts` for a shop on Luigi's Box, the latter with the client's own rules; `src/lib/services/shops/super-pharm.test.ts` for one on Algolia, with POST bodies and the pinned-price rules; and `src/lib/services/product-search.test.ts` for the list's search across the shops.
- **Run locally**: `npx vitest run src/lib/services/shops/<shop>.test.ts`, or the whole suite with `npm run test`.

### 6.5 Adding a production check

- **Location and naming:** a production check is a step in `scripts/check-production.mjs`, in one of its three groups:
  - `pages`: the app's signed-out answers. Needs `CHECK_APP_URL`.
  - `sign-in`: the one Auth probe.
  - `settings`: Auth's own settings. Needs `CHECK_SUPABASE_URL` and `CHECK_SUPABASE_KEY`.
    The deploy gate's comparison lives in `scripts/check-migrations-applied.mjs`, and `scripts/deploy-checked.mjs` chains the gate and the check around `npx wrangler deploy`.
- **Expected values** come from the code's contracts and smoke's signed-out steps (`scripts/smoke.mjs`), never from what production answers. A step asserts a status with the exact `Location`, the headers it names, or the page's text, never a status alone (risk #2's anti-pattern).
- **What a step may send:**
  - Nothing signed in: no cookie and no session.
  - Nothing that writes, and nothing that reaches a shop.
  - A POST only where the app refuses it before any write: the middleware's 302, the origin check's 403, a removed route's 404.
  - The one exception is the `sign-in` probe: one sign-in for `production-check@example.com`, an address no one has, which Auth refuses with `?error=invalid` only while the Worker's key works.
- **Output:**
  - One `PASS|FAIL  <step>  -> <observed>` line per step, with an `expected …` line under a FAIL.
  - Never a key, a body, the Supabase URL or a link. CI's logs are public, and a check run's link carries the Cloudflare account id.
  - A step that throws is named by its error's code or name, never its message (`failureOf`).
- **Its tests:**
  - The pure verdicts are tested in `scripts/check-production.test.mjs`; Vitest includes `scripts/**/*.test.mjs`.
  - CI's `smoke` job runs `pages` and `sign-in` against the workerd preview and the local stack, where they must pass. It runs `settings` against the local stack, where it must fail on open sign-up (`disable_signup=false`): the check's own negative test.
  - A new step needs a deliberate break that turns it red: break the behaviour it protects, or drop the text it asserts, and see its FAIL. Against a preview with no Supabase configured, `--only=pages` fails on the configuration banner.
- **Run by hand** with the variables inline, never from a file: `CHECK_APP_URL=<app origin> CHECK_SUPABASE_URL=<project URL> CHECK_SUPABASE_KEY=<publishable key> npm run check:production`, optionally with `--only=` or `--skip=`. Against the local preview, `CHECK_APP_URL` is `http://localhost:4321`.
- **References:**
  - The check: `scripts/check-production.mjs` and `scripts/check-production.test.mjs`.
  - The gate: `scripts/check-migrations-applied.mjs` and its test.
  - The runbook: `context/deployment/deploy-plan.md`, "Checked deploys (rollout Phase 4)".

## 7. What We Deliberately Don't Test

Exclusions agreed during the rollout (Phase 2 interview, Q5). Future contributors should respect these unless the underlying assumption changes.

- **Pixel-perfect screenshot comparisons** of every page and theme — the design changes with most slices, so such diffs would break constantly; visual risks get targeted e2e assertions instead. Re-evaluate if a visual regression reaches production twice. (Source: Phase 2 interview Q5.)
- **The dev-only kitchen sinks** (`/dev/product-page`, `/dev/watchlist`) — served only by `astro dev` and never shipped. Re-evaluate if they become the review baseline for the views. (Source: Phase 2 interview Q5.)
- **Coverage targets** — no coverage percentage is tracked, and rules already covered by boundary tables get no new tests for the number's sake. Re-evaluate if mutation testing (Module 3 Lesson 2) shows assertions that miss regressions. (Source: Phase 2 interview Q5.)
- **Live shop calls in any automated suite** — tests and CI never call a shop (`CLAUDE.md` non-negotiables, `roadmap.md:80`); live drift is a monitoring concern. Re-evaluate only through an official shop feed. (Source: project rule.)

Edges rollout Phase 2 found and the owner accepted rather than fixed (2026-10-07). Each is a known behaviour, so a test may pin it but mustn't expect it gone. (Source: `context/archive/2026-10-07-testing-route-and-database-seams/research.md`, Open Questions.)

- **The selected row beside a product** — from lg, its tag follows the island's live prices, while its screen-reader line and the chips' counts stay the list's own read. Re-evaluate if a screen-reader user meets the mismatch.
- **A block report that fails** — after a 403 or a challenge the gate answers `blocked` to its caller even when it can't record the block, and the shop stays switched on for every other path and user. Re-evaluate if a failed report ever shows in the logs.
- **Search text the schema admits** — the search schema checks characters and length only, so text such as `../../etc/passwd` or `union select password from users` passes, and whether a shop's firewall would flag it is unknown and must not be probed. Since `add-from-other-shops` (2026-10-09) each search sends the text to all four shops, so one refusal can stop any of them. Re-evaluate if a shop stops after a search.
- **A stale decision that matches the newer one (ABA)** — a re-pin's form names the state and the item it replaces, not a version. So a stale form still lands when its content matches the newer decision, as after a decline, a re-pin and a decline again. It writes the same content over the newer decision. Re-evaluate if decisions gain anything a stale tab could lose, such as who decided and when.
- **The id probe** — the table-wide insert grants let a caller choose a row's id. Someone who already knows a product's UUID, say from a shared link, could learn through a duplicate-key error whether it exists. No route posts an id for an insert, and closing it needs a column-level insert grant, a migration. Re-evaluate before inviting more people.
- **The pages' four recorded differences** — each page stays honest in its own way:
  - a decision whose time doesn't parse is unread on the product page only;
  - the product page reads prices after its lookups, so it can show a match the list beside it doesn't have yet;
  - the island and the selected row's tag move to the browser's clock once loaded;
  - the product page's price read, the heavier view with each item's history, can time out on its own.

  The seam table pins the two a stub can serve. Re-evaluate if a shopper meets one at the shelf.
