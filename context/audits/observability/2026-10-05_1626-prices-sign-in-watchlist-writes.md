# Observability audit — prices, sign-in and links, watchlist writes (2026-10-05)

The question, per flow: when this breaks in production, will anyone find out, and will they be able to tell why? The code audited is S-07's pull request head (`71e375b`), the code about to land on `main`. The audit is static only, by the owner's choice: every claim cites the code, and the most severe ones were re-read by hand (§ 8).

## 1. TL;DR

- **Nothing turns a failure into a person being told.** There is no error tracker and no alert. Every app log line is a `console.warn`, failures answer 302 or 200, and Astro turns exceptions into 500s whose invocation outcome is `ok`. The runbook's `wrangler tail --status error` filters by outcome, so it sees none of it.
- **Users get an honest gap; the owner gets nothing.** The PRD's "show the gap, never a wrong number" rule is built everywhere, but no failure gets a second channel to the responder. App faults read as a shop's "chwilowo niedostępna", and an Auth outage reads as everyone being signed out.
- **"Nothing" is trusted and stored.** An empty or filtered shop answer, a field value nobody recorded, and zero affected rows all become durable, plausible states: `missing`, `not_found`, "not orderable", "already decided" and "gone". Some of them are shared by every user who watches the item.
- **Each log helper keeps a different half of the error.** watchlist.ts and matches.ts keep the message, prices.ts the code, a shop step only the error's name. No line keeps a status, a stack, a shop, an operation or a request id. Meanwhile the platform keeps full query strings: link tokens and users' searches.
- **The single most important consequence:** a rotated Luigi's Box tracker, an unpushed migration or an Auth outage would show users plausible "temporary" or "signed out" states for days. The owner would learn only from a user, and by then the only evidence, a warn line, could have aged out of Workers Logs.

## 2. Capture model

- **Runtime.** Astro 7.3.2 SSR on Cloudflare Workers (workerd, `nodejs_compat`), through `@astrojs/cloudflare` 14.3.1 (`wrangler.jsonc` main `@astrojs/cloudflare/entrypoints/server`). With `output: "server"`, every page and route renders on demand, and pages stream (`BaseApp` streams by default, `node_modules/astro/dist/core/app/base.js:73`). React 19 islands hydrate in the browser. There is no background work: no cron, queue or `waitUntil` (the adapter exports only `fetch`).
- **Data and calls.** Supabase through `@supabase/ssr` with the publishable key only, one client per request, built in `src/middleware.ts:15` and kept in `locals.supabase`. Shops are called only through `gate.fetch` (`src/lib/services/shop-gate.ts`), which reserves a slot per request through a `security definer` RPC, never follows redirects, pauses on 429/503 and stops a shop on 403 or a challenge.
- **Error tracker:** none. `package.json` has no Sentry, Toucan, OpenTelemetry or similar dependency, and nothing calls a capture API.
- **Capture boundaries.** The only one is Astro's `render()` try/catch (`node_modules/astro/dist/core/routing/handler.js:101-108`). It writes one plain-text `console.error` line with the stack, then answers the 500 route. There is no `src/pages/500.astro`, so the answer is an empty 500 (`errors/default-handler.js:105`).
  - Errors after the first streamed byte only error the stream (`runtime/server/render/astro/render.js:66-73`): the browser gets a 200 with truncated HTML, and Astro logs nothing.
  - Astro's `checkOrigin` runs before the middleware and answers an unlogged plain-text 403.
  - The browser has no `error`, `unhandledrejection` or `astro:hydration-error` listener and no error boundary.
- **Logging.** The app has 8 `console.warn` calls, each writing one JSON line `{event, reason, detail}`: `src/lib/services/watchlist.ts:338`, `matches.ts:630`, `prices.ts:295`, `shop-gate.ts:265`, `shop-matching.ts:192` and `:380`, `shops/luigis-box.ts:349` and `shops/rossmann.ts:272`. None uses `console.error`, and the auth layer (`src/lib/services/auth.ts`, `src/middleware.ts`, `src/pages/api/auth/*.ts`) logs nothing.
- **Platform.** Workers Logs, with `"observability": { "enabled": true }` (`wrangler.jsonc:13-15`): every invocation sampled, plus console output. There is no logpush, tail consumer, trace or `issues` setting, and no notification is documented. Retention is about 7 days on Workers Paid (Cloudflare's published figure, not verifiable from the repo; `context/deployment/deploy-plan.md:303` still quotes the Free plan's 3 days).
- **Scrubbing.** By design, no emails or tokens are written. The gate blanks all-digit path segments and never logs query strings or bodies (`shop-gate.ts:29-31`), and a shop step's error keeps only its name, since a message could quote a search (`shop-matching.ts:367-381`). `redact_query_string` is unset (default `false`, `node_modules/wrangler/config-schema.json:3966-3971`), so invocation logs keep full URLs: `/auth/confirm?token_hash=…` (accepted as S-07 review F2) and users' `?q=` searches.
- **Deploy identity.** Workers Builds deploys each merge to `main` as a Worker version. Log lines carry no version or commit; the platform tags each event with its script version. There is no `version_metadata` binding and no source maps. The server chunks are unminified with `//#region src/…` markers, so stacks are readable but don't map to source lines. Only production traffic reaches Workers Logs (`preview_urls: false`).

## 4. Systemic root causes

1. **Nothing turns a failure into a person being told.**
   - Mechanism: no tracker, alert or notification. Astro converts exceptions into 500s with outcome `ok`, the app converts everything else into 302s and 200s, every app line is a `warn`, and the runbook's `--status error` keys on outcomes.
   - Why: the MVP chose Workers Logs only (`context/foundation/roadmap.md:72`, "no error tracking"), a reasonable cut for a handful of users. But `context/foundation/test-plan.md:192` names "monitoring" as the owner of live shop drift, and nothing implements it.
   - Explains: X1, X4, X6, X9, X10, X11, P8, P10.
2. **Graceful degradation without a second channel.**
   - Mechanism: every failure becomes a visible gap or a coded redirect for users, while the responder gets at most a warn line and often nothing.
   - Why: the PRD's guardrails were built thoroughly for users, but no requirement asked for a responder signal.
   - Explains: P4, P5, P6, S1, S3, S4, S6, W2.
3. **"Nothing" is trusted and persisted.**
   - Mechanism: empty answers, filtered hits, unknown field values and zero affected rows become durable states, some of them shared by every watcher of an item.
   - Why: "nothing found" and "already decided" are legitimate outcomes, and each check was written for its legitimate case.
   - Explains: P1, P2, P3, W1, W5.
4. **Privacy trimming was done per helper, not in one safe helper.**
   - Mechanism: each logger drops a different half of the error. No stack, status, cause, shop, operation or request id survives, while the platform keeps full query strings.
   - Why: each helper was written to keep user data out, which was right, but none kept the parts that carry no user data.
   - Explains: X2, X5, X8, X12, P7, S4.
5. **In the auth layer, null means three things.**
   - Mechanism: "no session", "Auth failed" and "refused" are the same null or false (`getUser`, `getClaims`). There is no timeout, and the per-request client defeats auth-js's refresh-failure cooldown.
   - Why: fail-closed is right for access, but the reason is thrown away along with the result.
   - Explains: S1, S2, S3, S5.
6. **There is no canary and no runtime version check.**
   - Mechanism: shop drift and schema drift are found by users, or by the owner running `supabase migration list --linked` by hand. The research note's per-adapter health check (§7: known EAN → expected fields) isn't built.
   - Explains: P1, P2, P3, W4, X11.

## 6. Recommended fix order

Ordered by blindness removed per unit of effort. Each step names the findings it closes.

1. **One shared failure reporter with levels.** Closes X2, X4, X5 and P7, and is the base of S4 and S5.
   - What: one module writing `{event, step, shop?, op?, name, code, status, hint?, stack?, version?}` at `console.error` for faults and `console.info` for expected outcomes.
   - Constraints: never a message that can hold user text, never an email or a token; a stack holds code locations only, so it may stay. `AuthSessionMissingError` and "nothing found" are routine (X4's trap).
2. **An alert, and a runbook that can see.** Closes X1, and makes X6, X9, X10 and X11 visible.
   - What: a tail consumer Worker that forwards error-level lines and HTTP ≥ 500 to the owner (e-mail or a webhook), or a dashboard notification if one fits; then correct `deploy-plan.md:303` and `infrastructure.md:88`.
   - Constraint: the free and paid limits of whatever channel the owner picks; this is the owner's call.
3. **The auth layer reads its errors.** Closes S1, S3, S4 and S6; S2 follows with a timeout.
   - What: the middleware and `isLinkSession` log non-routine Auth errors; retryable ones answer 503 instead of the sign-in redirect; set-password stays fail-closed but shows a notice; `global.fetch` with a timeout for the Supabase client.
4. **Distrust empty answers.** Closes P1, P2 and P3.
   - What: a multi-id batch with zero item hits, a non-empty search with zero item hits, and a non-problem+json Rossmann 404 become `failed`. Rossmann's search gets the all-dropped guard; Natura and Rossmann get odd-value counters.
   - Constraint: a genuinely delisted item must still read as `missing`, so the rule keys on "every id missing at once", not on one.
5. **Zero-row writes are re-checked.** Closes W1, and with W3 gives a baseline.
6. **`redact_query_string: true`.** Closes X8 and S-07's accepted F2.
   - Constraint: only after step 3 logs the auth outcomes, since the `?error=` codes in URLs are the auth flow's only accidental trace today.
7. **A browser beacon and an error boundary.** Closes P4.
   - What: a small JSON route (`refuseJsonRequest`, a size cap, no user text) logging event, component, error name and path without query; an error boundary around the island; a distinct text for app-side failures.
8. **The island reads `saved`, and gate failures get their own reason.** Closes P5 and P6.
9. **Deploy identity.** Closes X12 and X11: `version_metadata` with a `version` field on every line, `upload_source_maps`, and build-failure notifications.
10. **A daily canary,** with FR-015's Cron Trigger. Turns P1, P2, P3 and W4 into signals before users notice.
    - What: one known item per shop with its expected fields, and a schema-version check, logged at error level.
    - Constraint: the gate's reservation RPC is granted only to `authenticated` (`src/lib/services/shop-gate.ts:160-171`), so a scheduled run needs its own identity under the cap. It starts outside Astro's try/catch and every page boundary.
