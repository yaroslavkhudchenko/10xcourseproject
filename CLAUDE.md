# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Drogeria Radar: a private, invite-only web app for a handful of users that shows which of five Polish drugstore chains (Rossmann, Hebe, Super-Pharm, dm, Drogerie Natura) sells a repeat-purchase product cheapest today, with regular and promo price, the Omnibus 30-day low and the age of every price. Astro 7 SSR, React 19 islands, Tailwind 4 and Supabase (Postgres, auth, RLS) on Cloudflare Workers, bootstrapped from `10x-astro-starter` on 2026-09-20. The starter's demo pages (`src/pages/index.astro`, `src/pages/dashboard.astro`) and welcome components are placeholders, not product code.

Canonical documents (read them; do not restate them here):

- @context/foundation/prd.md — requirements FR-001…FR-015, guardrails, access model, open questions. FR ids are the shared vocabulary for features.
- @docs/research/polish-drugstore-price-apis.md — verified shop endpoints, response shapes, quirks, blocked shops and dead ends (Appendix C). Consult it before writing or changing a shop adapter; do not re-probe what it rules out.
- @context/foundation/tech-stack.md — why this stack. @README.md — starter setup and deployment details.

## Non-negotiables

- Sign-up is invite-only with no open registration (PRD FR-001). The starter's `/auth/signup` page and `enable_signup = true` in `supabase/config.toml` are inherited defaults, not the product's registration path. The production Supabase project has "Allow new users to sign up" off; never run `supabase config push` against it, because that pushes `enable_signup = true`.
- Watchlists are private per user; price observations are shared by everyone who watches the same shop item and hidden from everyone else (FR-005), so no one can list what others watch. Enforce this with RLS policies, not only with query filters. Removing a watchlist entry hides it and never deletes observations.
- Every displayed price shows its source and fetch time (FR-010, FR-011). A failed fetch shows the last known price with its age or a visible gap, never a blank, a zero or a silently stale value. Online prices are labelled as online; never claim shelf prices.
- Shop fetches run server-side and on demand (FR-008), under a per-shop request cap for the whole deployment, and stop for a shop that blocks or asks. Never circumvent bot protection; Sephora, Douglas and Notino are excluded for that reason. dm is out of the MVP for the same reason: its search refuses Cloudflare Workers traffic (research §9), so don't build a dm adapter or a proxy for it.
- Every shop request goes through `gate.fetch` from `src/lib/services/shop-gate.ts`; never call `fetch` on a shop host directly, and add a new host to `SHOP_HOSTS` before calling it. The gate allows `public.shops.cap_per_minute` requests per shop (30 by default) in any 60 seconds, never follows redirects, pauses a shop after a 429 or a 503 with Retry-After, and stops it after a 403 or a bot challenge until the owner sets `enabled` back to true in `public.shops`. It needs the signed-in user's Supabase client (`shopGateFor(supabase)`): without one, every call is skipped as `unavailable`. Callers read an `ok` body promptly, because the gate's 8 s timeout covers the body too, and show a read error as a gap. Lookup tests assert which URLs the replay fetch served, because a miss looks like `failed/network`. User search text is validated with zod, for allowed characters and length, before it goes into a shop URL, because one 403 stops the shop for everyone.
- The confirmed per-shop item is the anchor and EAN only a helper (FR-004, FR-006): Hebe returns wrong EANs and Super-Pharm's search index has none.
- Read `SUPABASE_URL` and `SUPABASE_KEY` only through `astro:env/server` (declared in `astro.config.mjs` as optional server secrets), never `import.meta.env`.
- The HTML-comment-delimited lesson block at the bottom of this file belongs to the 10x CLI and is replaced on every `npx @przeprogramowani/10x-cli get <lesson> --type rules`. Project rules live above it; never edit inside it.

## Commands

Prerequisite: copy `.env.example` to both `.env` (Node processes: build, check, smoke) and `.dev.vars` (the Cloudflare dev runtime) and fill in the two Supabase values. Without them the app still runs, but auth is disabled and every page shows an error banner.

- `npm run dev` — dev server on the Cloudflare workerd runtime at http://localhost:4321. Under an AI agent, `astro dev`, like `--background`, backgrounds the server and kills it if it isn't ready within 30 s, and a start after `astro sync`, `astro check` or `npm run build` takes longer: they invalidate Vite's dependency cache. So start `ASTRO_DEV_BACKGROUND=1 npx astro dev` as a background task, which skips the agent detection and its limit; `npx astro dev stop` still stops it. If the first start after that crashes with "The file does not exist at …node_modules/.vite/deps_ssr/…", start it again.
- `npm run build` / `npm run preview` — production build via `@astrojs/cloudflare`; preview serves `dist/` on workerd. The build copies `.dev.vars` into `dist/server/`, so rebuild after changing it. Preview keeps running as a background server, and a second `npm run preview` silently reuses it; run `npx astro preview stop` before rebuilding.
- `node scripts/check-built-fonts.mjs` — after `npm run build`, checks that the build shipped its web fonts, which it downloads from Google Fonts: a build that can't reach them still succeeds, with only a warning and no font files. CI runs it in the `ci` job, after its build.
- `npm run lint` / `npm run lint:fix` / `npm run format` — ESLint (type-checked rules with the Astro and React plugins) and Prettier.
- `npx astro sync && npx astro check` — generate `.astro/types.d.ts`, then type-check `.astro` and TS files. CI runs both. On a fresh checkout run `astro sync` before `lint` or `check`; both depend on the generated types.
- `npm run smoke` — dependency-free auth-flow smoke test (`scripts/smoke.mjs`) against a running server, `BASE_URL` defaulting to localhost:4321. Needs a reachable Supabase with email confirmation off.
- `npm run test` — Vitest over `src/**/*.test.ts`, in Node rather than workerd; CI runs it in the `ci` job. Run one test with `npx vitest run <file> -t "<name>"`. Tests never reach live shops: they serve recorded responses through `createReplayFetch` (`src/lib/services/testing/replay-fetch.ts`). Shop fixtures live in `src/lib/services/shops/fixtures/`: real answers recorded once with `curl` using the gate's User-Agent, at least 2 seconds apart, never from CI.
- `node scripts/check-shop-gate-db.mjs` — checks the shop gate's SQL functions, RLS and grants against the local Supabase; CI runs it in the `smoke` job. It needs `npx supabase start` and the local stack's URL and anon key in `SUPABASE_URL` and `SUPABASE_KEY`. Its rows persist, so run `npx supabase db reset --local` before a rerun. A reset also deletes every local user, including the owner's own test account, so say so before running it; sign up again at `/auth/signup` afterwards.
- `node scripts/check-watchlist-db.mjs` — proves with two throwaway users that watchlist rows stay private to their owner (RLS and grants); CI runs it in the `smoke` job. It needs the same local stack and variables, and signs up fresh users each run, so reruns need no reset.
- `node scripts/check-matches-db.mjs` — proves with two throwaway users that shop matches stay private to their owner, attach only to the owner's own products and never change once matched or declined, and that `watchlist_items` and `watchlist_matches` refuse values outside their bounds; CI runs it in the `smoke` job. It needs the same local stack and variables and, like the watchlist check, signs up fresh users each run, so reruns need no reset.
- `node scripts/check-prices-db.mjs` — proves with two throwaway users that only a shop item's watchers read and add its price observations, the view included, and that no one can change or delete one or set its time, source or recording user; it also checks S-03's EAN and match-update rules on the watchlist tables. CI runs it in the `smoke` job. It needs the same local stack and variables, and each run uses fresh users and shop item ids, so reruns need no reset and no real product gets a test price.
- `npx supabase start` / `npx supabase stop` — local Supabase via Docker (API on 54321, Studio on 54323, settings in `supabase/config.toml`). Apply new migrations to the running stack with `npx supabase migration up --local`: unlike `db reset --local`, it keeps local users. Never run `migration up --linked`, which would apply them to production.
- Production deploys by merging to `main`: Cloudflare Workers Builds runs `npm run build` and `npx wrangler deploy` for the Worker `drogeria-radar`. A manual `npx wrangler deploy` is for emergencies only, from a clean `main` after `npm run build`. Set secrets with `npx wrangler secret put SUPABASE_URL --name drogeria-radar` and the same for `SUPABASE_KEY`. What is live, and how to roll back: `context/deployment/deploy-plan.md`.

## Architecture

- **Request lifecycle**: `output: "server"`, so every page and API route renders on demand. `src/middleware.ts` runs on each request: it builds the request's only Supabase client and keeps it in `Astro.locals.supabase`, stores the user in `Astro.locals.user` (both typed in `src/env.d.ts`) and redirects unauthenticated requests whose path starts with an entry of `PROTECTED_ROUTES`. Gate new pages by adding them there. Pages and routes use `locals.supabase` and never create a second client: `@supabase/ssr` sends its cache headers when it writes auth cookies, and only the middleware's client carries them to the response. Every signed-in response is `Cache-Control: private, no-store`.
- **Null-client contract**: `createClient()` in `src/lib/supabase.ts` returns `null` when the env is missing, and `locals.supabase` is then null; the middleware, the auth API routes, the watchlist pages and routes (`/watchlist`, `/watchlist/<id>`, `/api/watchlist`, `/api/watchlist/matches`, `/api/watchlist/prices`, `/api/watchlist/refresh`) and `src/lib/config-status.ts` (rendered as a banner by `src/layouts/Layout.astro`) all tolerate that. New Supabase code keeps this contract unless the contract is removed deliberately everywhere.
- **API routes**: `src/pages/api/**` export uppercase handlers (`export const POST: APIRoute`). The auth routes take HTML form posts and redirect back with an `?error=` query param that the page reads; their React islands (`client:load`) add only client-side validation and the password toggle. Reuse this shape for new forms, with one change: redirect with an error code that the page maps to its own text, as `/api/watchlist` does, so a crafted link can't put words on the page (the auth routes predate this and pass Supabase's message). Validate input with zod via `import { z } from "astro/zod"` (no extra dependency); the auth routes predate that rule and cast form fields. A JSON route, such as `/api/watchlist/prices`, accepts only `application/json` and refuses other sites itself with `refuseJsonRequest` (`src/lib/json-request.ts`), because Astro's `checkOrigin` refuses cross-site posts of form content types only.
- **Workers constraints**: requests are short-lived and the runtime is workerd with `nodejs_compat`, not full Node. The post-MVP daily refresh (FR-015) needs a Cron Trigger or a queue, not a request handler.
- **UI**: `/watchlist` is the main screen, and the app's own text is Polish (`<Layout lang="pl">`); the starter's English pages stay until S-07. `/watchlist/<id>` is a product's page, which "Dodaj" and each list entry lead to. It shows each matched shop once, as its price row with its "Zobacz w sklepie" link, and its Natura section (`src/components/watchlist/NaturaSection.astro`, with states from `src/lib/services/natura-view.ts`) holds only the matching decision. Without one, it looks the product up in Natura, but, like the search, only on the user's own navigation (`isOwnNavigation`), so a link from another site can't spend the cap everyone shares. The page's prices come from the React island `src/components/watchlist/PriceComparison.tsx`, which shows the stored prices at once and, again only on the user's own navigation, refetches each shop last checked more than 15 minutes ago through `/api/watchlist/prices`, one request per shop, so each row updates as its shop answers. The list shows stored prices only and asks no shop; its "Odśwież ceny" posts to `/api/watchlist/refresh`, as the island's button does without JavaScript. Freshness and the cheapest shop are decided only in `src/lib/services/price-comparison.ts` (stale after 24 hours; only fresh prices orderable online can win), which the island imports with `src/lib/shop-messages.ts` and `src/lib/json-request.ts`, so none of them imports anything server-only. Astro components for static markup, React only where interactivity is needed. Tailwind 4 through the Vite plugin with no `tailwind.config`. Design tokens are CSS variables in `src/styles/global.css` (shadcn "new-york", oklch), with a light theme in `:root` and a dark one in `.dark`. The `theme` prop of `src/layouts/Layout.astro` either lets the user's choice, stored, else the system's, pick the theme before the first paint through an `is:inline` head script (the default), pins a page to dark (`/`, `/dashboard` and `/auth/*` until S-07), or pins it to light; a new role gets a value in `:root` and in `.dark` and a `--color-*` entry in `@theme inline`. `scripts/check-token-contrast.mjs`, which CI runs, reads `:root` and `.dark`, where every custom property must be an `oklch()` colour or a `var()` of another in the same block (the non-colour ones are on its allow-list), and checks the text, focus and field-border pairs listed in it over each theme's paper and its dots, so a new pair or value must pass it. Components live in `src/components/ui/` (button, card, alert, badge), so check there first; a missing one is copied from `https://ui.shadcn.com/r/styles/new-york-v4/<name>.json`, not added with the shadcn CLI, which would add the `cn` and `radix-ui` packages: import `cn` from `@/lib/utils` and `Slot` (the registry's `Slot.Root`) from `@radix-ui/react-slot`, and record the URL, the date and every change from the registry in a header comment. A new variant goes into the component's `cva` variants, as `success`, `warning`, `touch` and `underlined` did; merge classes with `cn()` from `@/lib/utils`, and put Alert text inside `AlertDescription` or `AlertTitle`, since bare text lands in the Alert's zero-width icon column. In `.astro` files these React components render as static HTML without `client:*`. Astro's React renderer drops a `class` prop, so pass `className`, and it hands children over as an HTML string that `asChild` can't style, so a link styled as a button is `class:list={cn(buttonVariants({ … }), …)}`. Astro drops the space at a line break between text and an element, or between two expressions, so write that space as `{" "}`. The product page's files (`src/pages/watchlist/[id].astro`, the `.astro` and `.tsx` files under `src/components/watchlist/`, and the `.astro` and `.ts` files under `src/dev/`) use tokens and components only: `tokenConfig` in `eslint.config.js` refuses Tailwind palette classes, arbitrary px/rem values and arbitrary colours there, so a newly cleaned view joins its `files`. The product page's own shared pieces are `ProductTitle.tsx` (its title row, in the island), `ShopLink.tsx` (the one "Zobacz w sklepie" link), `NaturaSection.astro` and `PriceComparisonView.tsx` in `src/components/watchlist/`, with the notice codes and texts in `src/lib/notices.ts`, and a flush text link is the Button's `inline` size. `/dev/product-page` (`src/dev/product-page.astro`, fixtures in `src/dev/fixtures.ts`) shows every state of the product page, only under `astro dev` (an inline integration in `astro.config.mjs`), so update it with the view; Tailwind doesn't scan `src/dev` (`@source not "../dev"`), so a class used only there gets no CSS. Path alias `@/*` maps to `src/*`.
- **Shops and matching**: product search is Rossmann's, through `src/lib/services/shops/rossmann.ts`, and Natura is matched through `src/lib/services/shops/natura.ts` (Luigi's Box). Natura's tracker id is the constant `NATURA_TRACKER_ID`: when Luigi's Box answers 404 `Catalog for tracker_id: "…" not found` (logged as "tracker id rejected"), take the new id from Natura's page (research §2.5) and update the constant and the Natura tests' expected URLs, which pin it. The matching rule lives in `src/lib/services/matching.ts`: exactly one candidate sharing an EAN and the size with the product is accepted automatically; otherwise the user picks among the candidates or declines them all. Pinned items' prices come from Rossmann's v2 detail by id, one product per request since no batch route is known (`fetchRossmannPrice`), and from Luigi's Box filtered by SKU, one repeated `f[]=sku:<SKU>` per SKU and up to 50 per request, with `hit_fields` naming only the price attributes (`fetchNaturaPrices`; research §2.1, §2.5). `refreshPrices` (`src/lib/services/price-refresh.ts`) fetches both through the gate and stores what the shops answer. A stored id is user input: a Rossmann id must be all digits before it becomes a path, because the gate checks the host, not the path, and a `..` segment would reach another path.
- **Data**: migrations go in `supabase/migrations/` named `YYYYMMDDHHmmss_short_description.sql`, with RLS enabled on every table and per-operation, per-role policies. The production project doesn't expose new tables to the Data API automatically, so every migration also grants table privileges explicitly: to `authenticated`, and to `anon` only where that's intended. It has automatic RLS on as a safety net. A table reached only through `security definer` functions gets no grants and no policies (`shops`, `shop_requests`). `watchlist_matches` holds each user's private decisions, one per product and shop: `matched`, `unmatched` (the user declined) or `not_found` (the lookup found nothing); RLS lets only a `not_found` row change before S-08 (re-pinning), and the update grant covers only the decision's columns. Foreign-key checks bypass RLS, so its composite foreign key `(watchlist_item_id, user_id)` ties each match to its owner's product. `price_observations` holds every price check and is append-only: RLS lets only the shop item's watchers (users with the item on their list, or a `matched` match to it) read and add rows, and no grant or policy allows an update or a delete. Its column grants leave each row's time, source and recording user to the database and keep `recorded_by` unreadable, so an insert asks for no rows back and every read names its columns. A check that finds the item gone adds a `missing` row: the last price stays, marked out of date, and can't be named cheapest. The app reads `latest_price_observations`, a `security_invoker` view of each item's last check and last price. Accepted risks, to revisit before inviting more people: with no server-only key, a user can add a plausible fake price for any item, since watching one is self-service, and it counts as the item's last check, so its watchers' automatic refresh waits up to 15 minutes; and people watching the same item see each other's check times. The length and format checks on `watchlist_items` and `watchlist_matches` mirror `PRODUCT_LIMITS`, and the price bound on `price_observations` mirrors `PRICE_LIMITS` (both in `src/lib/services/product-limits.ts`), so changing a limit needs a migration too. Postgres lets `PUBLIC` execute every new function, so revoke that from `public, anon` and grant `execute` to `authenticated` explicitly. `auto_expose_new_tables = false` in `supabase/config.toml` gives the local stack the same grants as production, so a missing grant fails locally and in CI first. Migrations reach production only when the owner runs `npx supabase db push`, after a one-time `npx supabase login` and `npx supabase link --project-ref <ref>`; never `supabase config push`. After the owner's push, confirm it with `npx supabase migration list --linked` (read-only): the new migration must show a remote version before the PR that needs it merges; a dashboard check isn't enough on its own. If production answers PGRST205 ("Could not find the table … in the schema cache"), check that list before reloading the schema cache. Shared types (entities, DTOs) belong in `src/types.ts` and business logic in `src/lib/services/`.

## Tooling and repository conventions

- Pre-commit (husky + lint-staged) runs `eslint --fix` on `*.{ts,tsx,astro}` and `prettier --write` on `*.{json,css,md}`; a lint error blocks the commit.
- Prettier uses 120 columns and sorts Tailwind classes; let it reorder them.
- `.nvmrc` pins Node 24.18.0 (npm 11.16.0), and both CI and Workers Builds read it. Change dependencies with that npm. npm 11.6.2 writes lockfiles without the `@emnapi/*` entries that `npm ci` in npm 10.9 and 11.16 requires, so CI fails at install. Local Node below 24.16 prints non-fatal `EBADENGINE` warnings from `eslint-plugin-astro` at install.
- CI (`.github/workflows/ci.yml`) runs on pushes and PRs to `main`: lint, `astro check`, unit tests and build in the `ci` job, and the shop gate, watchlist, shop matches and price observations database checks and the smoke test against a local Supabase in the `smoke` job. It never deploys and needs no repository secrets; keep Cloudflare tokens and Supabase keys out of GitHub.
- `context/` is the 10x workflow surface: `foundation/` living docs are edited in place, `changes/<id>/` holds per-change artefacts created with `/10x-new`, and `archive/` is read-only (see @context/foundation/README.md).
- The 10x CLI (`npx @przeprogramowani/10x-cli@latest`) manages `.claude/`, `.10x-cli.json` and the course block at the bottom of this file, and tracks them by content hash. `.prettierignore` and `.gitattributes` (LF everywhere) keep them byte-identical, so never reformat them. Apply a lesson's course block with `get <lesson> --type rules`: in CLI 1.25.2 a plain `get` removes the block. After any `get` or `sync`, check that the block is still there and re-apply it if not. On Windows the CLI's manifest write sometimes fails with `EPERM` (the file is briefly locked), and some runs print nothing; rerun the same command.
- `CLAUDE.md.scaffold` is the starter's original rules file left by the bootstrap merge and `context/changes/bootstrap-verification/verification.md` is its audit log; Claude Code loads neither.
- Changes reach `main` only through pull requests. The `preventFailedDeploy` ruleset requires green `ci` and `smoke` checks, and every merge deploys to production through Workers Builds, so open the PR and leave the merge to the owner.
- The default branch is `main` of a public GitHub repository: never commit account IDs, emails, the workers.dev subdomain or key values. There is no enforced commit convention yet.

## 10xDevs AI Toolkit - Module 2, Lesson 1

Move from sprint-zero setup to project orchestration with the **roadmap chain**:

```
(Module 1 foundation docs) -> /10x-roadmap -> backlog-ready roadmap items
```

`/10x-roadmap` is the lesson focus. `/10x-new` is intentionally introduced in Module 2, Lesson 2, when a selected roadmap item becomes an implementation change folder.

### Task Router - Where to start

| Skill | Use it when |
| --- | --- |
| **Roadmap (lesson focus)** | |
| `/10x-roadmap` | You have `context/foundation/prd.md` and a scaffolded project baseline, and you need a vertical-first MVP roadmap. The skill reads the PRD, inspects the code baseline, uses available foundation docs such as `tech-stack.md`, `infrastructure.md`, and `deploy-plan.md`, then writes `context/foundation/roadmap.md`. Use it BEFORE creating per-change folders or implementation plans. |
| **Re-run upstream if needed** | |
| `/10x-shape` / `/10x-prd` / `/10x-tech-stack-selector` / `/10x-bootstrapper` / `/10x-agents-md` / `/10x-infra-research` | Bundled from Module 1 so foundation contracts can be fixed before roadmap sequencing. If roadmap generation exposes a PRD gap, repair the PRD before pretending the backlog is ready. |

### How the chain hands off

- `/10x-roadmap` bridges product and implementation. It does not choose frameworks, design schemas, or write a per-change implementation plan.
- The output is `context/foundation/roadmap.md`: ordered milestones, vertical slices, bounded foundations, dependencies, unknowns, risk, and backlog handoff fields.
- Roadmap items should receive stable human-readable identifiers in backlog tools. The actual `context/changes/<change-id>/` folder is created in Lesson 2 with `/10x-new`.

### Roadmap boundaries

- Default to vertical slices: user-visible outcomes that cross UI, data, business logic, and integrations.
- Horizontal work is allowed only as a bounded enabler that names the downstream vertical milestone it unlocks.
- Avoid orphan horizontal work such as "build the whole database", "build all API endpoints", or "design the whole UI" before the first user-visible flow.
- Roadmap is not a calendar estimate. Do not invent dates, story points, or sprint velocity unless the user explicitly asks for a separate planning artifact.

### Foundation paths used by this lesson

- `context/foundation/prd.md` - input
- `context/foundation/tech-stack.md` - optional input
- `context/foundation/infrastructure.md` - optional input
- `context/deployment/deploy-plan.md` - optional input
- `context/foundation/roadmap.md` - output
- `context/foundation/lessons.md` - recurring rules and pitfalls
- `docs/reference/contract-surfaces.md` - load-bearing names registry

Skills must not write to `context/archive/`. Archived changes are immutable; if a resolved target path starts with `context/archive/`, abort with: "This change is archived. Open a new change with `/10x-new` instead."
