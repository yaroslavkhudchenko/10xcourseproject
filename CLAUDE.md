# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Drogeria Radar: a private, invite-only web app for a handful of users that shows which of five Polish drugstore chains (Rossmann, Hebe, Super-Pharm, dm, Drogerie Natura) sells a repeat-purchase product cheapest today, with regular and promo price, the Omnibus 30-day low and the age of every price. Astro 7 SSR, React 19 islands, Tailwind 4 and Supabase (Postgres, auth, RLS) on Cloudflare Workers, bootstrapped from `10x-astro-starter` on 2026-09-20. No starter page remains: `/` (`src/pages/index.astro`) sends a signed-in user to `/watchlist` and a visitor to `/auth/signin`.

Canonical documents (read them; do not restate them here):

- @context/foundation/prd.md — requirements FR-001…FR-015, guardrails, access model, open questions. FR ids are the shared vocabulary for features.
- @docs/research/polish-drugstore-price-apis.md — verified shop endpoints, response shapes, quirks, blocked shops and dead ends (Appendix C). Consult it before writing or changing a shop adapter; do not re-probe what it rules out.

## Non-negotiables

- Sign-up is invite-only with no open registration (PRD FR-001): the app has no sign-up page or route and sends no email, and a person gets an account only from the owner, made in the Supabase dashboard or through an invite or recovery link the owner makes with `scripts/owner-link.mjs`. `[auth] enable_signup = true` in `supabase/config.toml` is there only so the local tests can sign throwaway users up through Auth; `[auth.email] enable_signup` is the whole email provider, which password sign-in needs, so it stays on everywhere. The production Supabase project has "Allow new users to sign up" off; never run `supabase config push` against it, because that pushes `enable_signup = true`. A secret key (`sb_secret_…`, or the legacy `service_role` JWT) bypasses RLS and is the owner's alone, for one `owner-link.mjs` run in their own shell: never put one into the app, the Worker, `.env`, `.dev.vars` (which the build copies into `dist/server/`), CI or a test.
- Watchlists are private per user; price observations are shared by everyone who watches the same shop item and hidden from everyone else (FR-005), so no one can list what others watch. Enforce this with RLS policies, not only with query filters. Removing a product deletes the user's own watchlist row and, through the cascade, their decisions for it, never an observation.
- Every displayed price shows its source and fetch time (FR-010, FR-011). A failed fetch shows the last known price with its age or a visible gap, never a blank, a zero or a silently stale value. Online prices are labelled as online; never claim shelf prices.
- Shop fetches run server-side and on demand (FR-008), under a per-shop request cap for the whole deployment, and stop for a shop that blocks or asks. Never circumvent bot protection; Sephora, Douglas and Notino are excluded for that reason. dm is out of the MVP for the same reason: its search refuses Cloudflare Workers traffic (research §9), so don't build a dm adapter or a proxy for it.
- Every shop request goes through `gate.fetch` from `src/lib/services/shop-gate.ts`; never call `fetch` on a shop host directly, and add a new host to `SHOP_HOSTS` before calling it. `SHOP_HOSTS` names only the hosts the adapters call: a shop's own pages, which candidates link to, are checked by its adapter and never fetched. ESLint refuses the global `fetch` in server code outside the gate (`serverFetchConfig` in `eslint.config.js`), the tests and their helpers aside. The gate allows `public.shops.cap_per_minute` requests per shop (30 by default) in any 60 seconds, never follows redirects, pauses a shop after a 429 or a 503 with Retry-After, and stops it after a 403 or a bot challenge until the owner sets `enabled` back to true in `public.shops`. Any other answer outside 2xx is `failed` (`http`) with its status and, when the answer names one, its media type (`contentType`, lowercased and without its parameters), never its body, so an adapter can tell two answers with the same status apart, as Rossmann's 404 rule does ("Shops and matching"). It needs the signed-in user's Supabase client (`shopGateFor(supabase)`): without one, every call is skipped as `unavailable`. Callers read an `ok` body promptly, because the gate's 8 s timeout covers the body too, and show a read error as a gap. Lookup tests assert which URLs, and for a POST which bodies, the replay fetch served, because a miss looks like `failed/network`. User search text is validated with zod, for allowed characters and length, before it goes into a shop request, because one 403 stops the shop for everyone.
- The confirmed per-shop item is the anchor and EAN only a helper (FR-004, FR-006): one EAN can come with another size in another shop (Hebe's 5,5 ml lip balm carries the EAN of Rossmann's 4,8 g one), Hebe's size field `Pojemność` is unreliable (the "wrong EAN" once reported for Hebe was that field, research §2.2), and Super-Pharm's search index has no EAN.
- Read `SUPABASE_URL` and `SUPABASE_KEY` only through `astro:env/server` (declared in `astro.config.mjs` as optional server secrets), never `import.meta.env`.
- The HTML-comment-delimited lesson block at the bottom of this file belongs to the 10x CLI and is replaced on every `npx @przeprogramowani/10x-cli get <lesson> --type rules`. Project rules live above it; never edit inside it.

## Commands

Prerequisite: copy `.env.example` to both `.env` (Node processes: build, check, smoke) and `.dev.vars` (the Cloudflare dev runtime) and fill in the two Supabase values. Without them the app still runs, but auth is disabled and every page shows an error banner.

- `npm run dev` — dev server on the Cloudflare workerd runtime at http://localhost:4321. Under an AI agent, `astro dev`, like `--background`, backgrounds the server and kills it if it isn't ready within 30 s, and a start after `astro sync`, `astro check` or `npm run build` takes longer: they invalidate Vite's dependency cache. So start `ASTRO_DEV_BACKGROUND=1 npx astro dev` as a background task, which skips the agent detection and its limit; `npx astro dev stop` still stops it. If the first start after that crashes with "The file does not exist at …node_modules/.vite/deps_ssr/…", start it again.
- `npm run build` / `npm run preview` — production build via `@astrojs/cloudflare`; preview serves `dist/` on workerd. The build copies `.dev.vars` into `dist/server/`, so rebuild after changing it. Preview keeps running as a background server, and a second `npm run preview` silently reuses it; run `npx astro preview stop` before rebuilding.
- `node scripts/check-built-fonts.mjs` — checks that the build shipped its web fonts, which `astro build` downloads from Google Fonts: a build that can't reach them still succeeds, with only a warning and no font files. `npm run build` runs it after `astro build`, so such a build fails wherever it runs: in CI, in Workers Builds, which then deploys nothing, and locally, offline too.
- `npm run lint` / `npm run lint:fix` / `npm run format` — ESLint (type-checked rules with the Astro and React plugins) and Prettier.
- `npx astro sync && npx astro check` — generate `.astro/types.d.ts`, then type-check `.astro` and TS files. CI runs both. On a fresh checkout run `astro sync` before `lint` or `check`; both depend on the generated types. While a dev server runs, type-check with `npx astro check --noSync`: the sync rewrites Vite's SSR dependency cache (`node_modules/.vite/deps_ssr`), and the running server then answers 500 on every page until it restarts.
- `npm run smoke` — dependency-free auth-flow smoke test (`scripts/smoke.mjs`) against a running server, `BASE_URL` defaulting to localhost:4321. It reads `SUPABASE_URL` and `SUPABASE_KEY` from `.env` (`node --env-file-if-exists=.env`) and refuses any Supabase but the local stack, because it signs its throwaway user up through Auth's own `/auth/v1/signup` (local sign-up on, email confirmation off). It pins the front door's redirects and return paths, the auth routes' codes and origin refusals, the confirm and set-password contracts and the removed pages' 404s, with no secret key and no shop request.
- `npm run check:production` — the signed-out, read-only check of a deployment (`scripts/check-production.mjs`), in three groups that `--only=` and `--skip=` select: `pages` (the front door's redirects, the protected routes, another site's form post, the removed pages, the Polish sign-in page without the configuration banner, a link's page, sign-out), `sign-in` (one sign-in for an address no one has, which Auth refuses with `?error=invalid` only while the Worker's key works) and `settings` (Auth's `disable_signup` and email provider). It reads `CHECK_APP_URL`, `CHECK_SUPABASE_URL` and `CHECK_SUPABASE_KEY` only from its environment, never from a file, refuses a secret key and an insecure URL before any request, holds no session, reaches no shop and prints no key, body or Supabase URL. Workers Builds runs it after each deploy (`npm run deploy:checked`), and CI's `smoke` job against the preview, where `settings` must fail on local open sign-up.
- `node scripts/check-migrations-applied.mjs` — whether every file in `supabase/migrations/` is applied to the database `CHECK_SUPABASE_URL` names, asked through `applied_migrations()` with the publishable key: it prints `All <n> migrations are applied`, or names the missing versions and exits 1, and reads an answer it can't read as a refusal, never as nothing missing. It is the deploy gate's first step, CI's `smoke` job runs it against the local stack, and it confirms a push by hand.
- `npm run test` — Vitest over `src/**/*.test.ts` and the scripts' `scripts/**/*.test.mjs`, in Node rather than workerd; CI runs it in the `ci` job. It leaves out `src/**/*.db.test.ts`, which need the local stack (`npm run test:db`). Run one test with `npx vitest run <file> -t "<name>"`. Tests never reach live shops: they serve recorded responses through `createReplayFetch` (`src/lib/services/testing/replay-fetch.ts`), which matches a request by its URL and its body: a recording that names one (`requestBody`), as every Super-Pharm recording does, since its POSTs all go to one Algolia URL, answers only exactly that body, and one that names none only a request without one. Shop fixtures live in `src/lib/services/shops/fixtures/`: real answers recorded once with `curl` using the gate's User-Agent, at least 2 seconds apart, never from CI.
- `npm run test:db` — Vitest over `src/**/*.db.test.ts` (`vitest.db.config.ts`): the tests that need the local stack, such as the real decision write in every stale-tab case (`matches.db.test.ts`). It needs `npx supabase start` and the local stack's URL and anon key in `SUPABASE_URL` and `SUPABASE_KEY`, refuses any other Supabase before any request, and signs up a fresh user each run, so reruns need no reset. CI runs it in the `smoke` job. How to add one is in `context/foundation/test-plan.md` §6.2.
- `node scripts/check-shop-gate-db.mjs` — checks the shop gate's SQL functions, RLS and grants against the local Supabase, including that anon can't send a block report, that a signed-in user can't write the shop tables or call `applied_migrations()`, that a refused reservation (capped, paused or stopped) inserts no request row, and that a shorter rate-limit report never shortens a longer pause; CI runs it in the `smoke` job. It needs `npx supabase start` and the local stack's URL and anon key in `SUPABASE_URL` and `SUPABASE_KEY`. It reads the request log's sequence as the local superuser through Docker (`requestLogMark` in `scripts/e2e-local-db.mjs`), so, like `check-prices-db.mjs`, it also needs Docker access to the local stack's database container and the local stack in `.env` and `.dev.vars`. Its rows persist, so run `npx supabase db reset --local` before a rerun. A reset also deletes every local user, including the owner's own test account, so say so before running it; the app has no sign-up page, so recreate that account afterwards in local Studio (Authentication → Users → Add user, with Auto Confirm User) or with an `owner-link.mjs` invite link.
- `node scripts/check-watchlist-db.mjs` — proves with two throwaway users that watchlist rows stay private to their owner, can't be changed and are removed only by their owner, after which the same product can be added again, and that a product added from another shop than Rossmann, here Natura, is such a row too, which no one can add to another user's list (RLS and grants); CI runs it in the `smoke` job. It needs the same local stack and variables, and signs up fresh users each run, so reruns need no reset.
- `node scripts/check-matches-db.mjs` — proves with two throwaway users that shop matches stay private to their owner, attach only to the owner's own products, change in any state only through their owner and never to another product, user or shop, and are deleted only with their product, and that `watchlist_items` and `watchlist_matches` refuse values outside their bounds; CI runs it in the `smoke` job. It needs the same local stack and variables and, like the watchlist check, signs up fresh users each run, so reruns need no reset.
- `node scripts/check-prices-db.mjs` — proves with two throwaway users that only a shop item's watchers read and add its price observations, the view included, that no one can change or delete one or set its time, source or recording user, that removing a product deletes none, so the item's other watchers keep its prices and the remover no longer reads or adds them, that a re-pin changes which item a user watches and ends the access to the old one's prices, that a user who watches nothing reads and counts none, and that a product added from Natura makes its own Natura item and its Rossmann match's item watched, by its owner only; it also checks S-03's EAN and match-update rules on the watchlist tables. CI runs it in the `smoke` job. It needs the same local stack and variables, and each run uses fresh users and shop item ids, so reruns need no reset and no real product gets a test price. Its history cases backdate checks through the local database container (`backdateChecks` in `scripts/e2e-local-db.mjs`), so it also needs Docker access to that container and the local stack in `.env` and `.dev.vars`.
- `node scripts/check-catalog-db.mjs` — holds the `public` schema to the reviewed list in the script of its relations and functions, each with its protection: RLS on every table, `security_invoker` on every view, no privilege of `anon` but EXECUTE on `applied_migrations()`, and nothing `PUBLIC` may execute. A migration that adds a table, a view or a function adds it to that list. It reads the catalogue as the local superuser through the database container (`sql` in `scripts/e2e-local-db.mjs`), so it needs Docker access to it and the local stack in `.env` and `.dev.vars`, and its self-test plants every fault in a transaction it rolls back. CI runs it in the `smoke` job.
- `node scripts/check-two-users.mjs` — against a running server bound to the local stack (`BASE_URL`, `http://localhost:4321` by default), user B gets for user A's product exactly what a product no one has gets, through every route and page that takes a product's id, each answer `private, no-store`, and changes nothing of A's; as A, the same comparison must differ. It needs the local stack's URL and anon key in `SUPABASE_URL` and `SUPABASE_KEY`, `.env` and `.dev.vars` pointing at the local stack, and Docker access to its database container, since it holds every enabled shop for its run and switches back on only those, also after Ctrl+C or a kill. It refuses to start while an e2e run or a manual `stop` holds the shops, checks that none is enabled before any request, and signs up fresh users each run. A new route or page that takes a product's id joins its list. CI runs it in the `smoke` job, against the preview after `npm run smoke`.
- `npx playwright test` — the Playwright e2e suite in `tests/e2e/`: Chromium at 390 × 844 with touch, against the workerd production preview, which the config builds and starts on 4321 (`E2E_PORT` overrides it); one spec with `npx playwright test tests/e2e/<name>.spec.ts`. It needs Docker, `npx supabase start` and the local stack in `.env` and `.dev.vars`, and the config refuses any other Supabase, because a run stops every enabled shop of the deployment it talks to. Each run signs up a throwaway local user through Auth, signs it in once through the Polish sign-in form ("E-mail", "Hasło", "Zaloguj się"), and holds every enabled shop under its own name: it refuses to start while another run or a manual `stop` holds them, switches back on only its own, also after Ctrl+C, and fails if a shop request was reserved meanwhile. It never reuses a server already on its port, so stop one there first (`npx astro dev stop`, `npx astro preview stop`) or set `E2E_PORT`. Give the command a timeout of several minutes, or run it in the background: a run killed outright leaves its shops stopped, and the next run refuses until `node scripts/e2e-local-db.mjs restore`. Never pass `--no-deps`, which skips the shop stop. Between runs, `node scripts/e2e-local-db.mjs stop` and `restore` hold the shops while you explore the app with playwright-cli; `restore` releases every e2e hold, so use it only while no run is going. How to add a spec is in `context/foundation/test-plan.md` §6.3. CI runs the suite in the `e2e` job.
- `npx supabase start` / `npx supabase stop` — local Supabase via Docker (API on 54321, Studio on 54323, settings in `supabase/config.toml`). Apply new migrations to the running stack with `npx supabase migration up --local`: unlike `db reset --local`, it keeps local users. Never run `migration up --linked`, which would apply them to production.
- `SUPABASE_URL=<project URL> APP_URL=<app origin> node scripts/owner-link.mjs <invite|recovery> <email>` — the owner's link for a person: an invite gives a new account its first password, a recovery a new one. Only the owner runs it, on their own machine, with the secret key in the shell's environment only, read with `read -rs SUPABASE_SECRET_KEY && export SUPABASE_SECRET_KEY` so it isn't shown or kept in the history, and `unset` after. It asks Auth's admin `generateLink`, which sends no email, and prints only `<APP_URL>/auth/confirm?token_hash=…&type=…` on stdout, the format `confirmFormSchema` takes. A link works once, for the Email OTP Expiration (86400 s, so 24 hours, with a 10-digit code: `otp_expiry` and `otp_length` under `[auth.email]` locally, which a running stack reads after `npx supabase stop` and `npx supabase start`, and the dashboard on production), and a newer link of the same type for the same email replaces it. The script refuses bad input, a key that isn't secret, an `APP_URL` with a path, and plain http anywhere but `localhost` or `127.0.0.1` before any request, and on a refusal prints only Auth's code with a hint: `email_exists` (make a recovery link) or `user_not_found` (make an invite link). Locally the key is `SECRET_KEY` from `npx supabase status -o env` and `APP_URL` is `http://localhost:4321`; production's steps, and the read-only check that production still refuses sign-up, are in `context/deployment/deploy-plan.md` ("Accounts and links (S-07)").
- Production deploys by merging to `main`: Cloudflare Workers Builds runs `npm run build` and `npm run deploy:checked` (`scripts/deploy-checked.mjs`) for the Worker `drogeria-radar`, with `CHECK_APP_URL`, `CHECK_SUPABASE_URL` and `CHECK_SUPABASE_KEY` (the publishable key) as build secrets. It refuses before anything when one is missing or unsafe, refuses to deploy code whose migration production lacks, runs `npx wrangler deploy`, then the production check, and any failure turns the build red; nothing rolls back on its own. A manual `npx wrangler deploy` is for emergencies only, from a clean `main` after `npm run build`, and skips both checks. Set secrets with `npx wrangler secret put SUPABASE_URL --name drogeria-radar` and the same for `SUPABASE_KEY`. What is live, how to roll back and what a red build means: `context/deployment/deploy-plan.md` ("Checked deploys (rollout Phase 4)").

## Architecture

- **Request lifecycle**: `output: "server"`, so every page and API route renders on demand. `src/middleware.ts` runs on each request: it builds the request's only Supabase client and keeps it in `Astro.locals.supabase`, stores the user in `Astro.locals.user` (both typed in `src/env.d.ts`) and redirects unauthenticated requests whose path starts with an entry of `PROTECTED_ROUTES` to sign-in: the list's or a product's page with itself as the way back, keeping only the list's filter (`signInHref(returnPathFor(url))`, such as `/auth/signin?next=%2Fwatchlist%2F<id>`), any other path, the API routes and `/auth/set-password` included, to the plain `/auth/signin`, which the product's island reads as an ended session. Gate new pages by adding them there. Pages and routes use `locals.supabase` and never create a second client: `@supabase/ssr` sends its cache headers when it writes auth cookies, and only the middleware's client carries them to the response. Every signed-in response is `Cache-Control: private, no-store`.
- **Null-client contract**: `createClient()` in `src/lib/supabase.ts` returns `null` when the env is missing, and `locals.supabase` is then null; the middleware, `/`, the auth pages and API routes (`/auth/signin`, `/auth/confirm`, `/auth/set-password`, `/api/auth/signin`, `/api/auth/signout`, `/api/auth/confirm`, `/api/auth/set-password`), the watchlist pages and routes (`/watchlist`, `/watchlist/<id>`, `/api/watchlist`, `/api/watchlist/matches`, `/api/watchlist/prices`, `/api/watchlist/refresh`, `/api/watchlist/remove`) and `src/lib/config-status.ts` (rendered as a banner by `src/layouts/Layout.astro`) all tolerate that. New Supabase code keeps this contract unless the contract is removed deliberately everywhere.
- **API routes**: `src/pages/api/**` export uppercase handlers (`export const POST: APIRoute`). A form route takes a plain HTML form post, which Astro's `checkOrigin` refuses from another site, guards `formData()`, validates the form with zod via `import { z } from "astro/zod"` (no extra dependency) and redirects back with an error code that the page maps to its own text (`src/lib/notices.ts`, where a code the app didn't send shows nothing), never a message, so a crafted link can't put words on the page: `/api/watchlist` and the auth routes do, the latter reading only an Auth error's `code` and `status` (`authErrorCodeOf`, `confirmErrorCodeOf` and `passwordErrorCodeOf` in `src/lib/services/auth.ts`). Reuse this shape for new forms. A JSON route, such as `/api/watchlist/prices`, accepts only `application/json` and refuses other sites itself with `refuseJsonRequest` (`src/lib/json-request.ts`), because Astro's `checkOrigin` refuses cross-site posts of form content types only.
- **Sign-in and links**: the auth pages are plain Astro forms in Polish that work without JavaScript and ask no shop; their rules (the zod schemas, Auth's errors as codes, each redirect) are in `src/lib/services/auth.ts` and their texts in `notices.ts`. A sign-in goes back to `returnPathOf(next)` (`src/lib/services/return-path.ts`): only `/watchlist` or `/watchlist/<uuid>` with at most a chip's `?f=`, anything else being `/watchlist`, because the landing counts as the user's own navigation, so a `next` carrying `repin`, `retry` or `q` would spend the shops' cap. A signed-in user opening `/auth/signin` goes there too. `signInHref`, beside `SIGN_IN_PATH` and `NEXT_PARAM` in the browser-safe `watchlist-rows.ts`, builds the link to sign-in with its way back, for the middleware and the island's "Zaloguj się ponownie". Sign-out ends this device's session only (`signOut({ scope: "local" })`) and lands on `/auth/signin?signed-out=1` ("Wylogowano."), a failed one on the list with its notice. An owner's link opens `/auth/confirm?token_hash=…&type=invite|recovery`, which only renders "Ustaw hasło", so a link preview can't use it up: only the button's post calls `verifyOtp` (on `locals.supabase`), and the page sends `no-store` and `Referrer-Policy: strict-origin`, not `no-referrer`, under which the browser would post its form with `Origin: null`, which `checkOrigin` refuses. `/auth/set-password` and its route accept only a session a link opened within the last 60 minutes (`linkSessionOf` on `getClaims()`'s `amr`) and send any other, a password sign-in's included, to the list before any update, so there's no change-password page; a new password has 8 to 72 UTF-8 bytes and lands on the list with "Hasło zapisane.".
- **Workers constraints**: requests are short-lived and the runtime is workerd with `nodejs_compat`, not full Node. The post-MVP daily refresh (FR-015) needs a Cron Trigger or a queue, not a request handler.
- **UI**: `/watchlist` is the main screen, and the app's text is Polish (`Layout`'s default `lang="pl"`). `/watchlist/<id>` is a product's page, which "Dodaj" and each list entry lead to. Both stand on `src/layouts/WatchlistShell.astro`, which wraps `Layout` in the dotted paper (`bg-paper`): from lg (1024 px) a header on top (`AppHeader.astro`: the logo, the search with its `/` shortcut, the theme switch, the account, its email from xl, and "Wyloguj"), the list in a 420 px column on the left (the `head`, `rows` and `footer` slots, the rows scrolling on their own) and the main pane (the default slot), which scrolls on its own; below lg a phone's screen, where the list's header is the logo and the account menu (`AccountMenu.astro`, a `<details>` that opens without JavaScript) and a product has its own row back to the list. The shell opens with a skip link to its `<main>` ("Przejdź do listy", "Przejdź do produktu"), shown only while it has the focus, and names the list beside a product by the list's heading (`listHeadingId`). The shell's pieces are in `src/components/shell/` (`AppHeader`, `AccountMenu`, `SearchForm`, `ThemeToggle`, `LogoMark`) and the list's in `src/components/watchlist/` (`ListHead` with the list's "Odśwież ceny", `FilterChips`, `ListRows` of `WatchlistRow`s with their `RowTag` price tags, `ListFooter` and `SearchResults`). The auth pages (`/auth/signin`, `/auth/confirm`, `/auth/set-password`) stand on `src/layouts/AuthShell.astro`, which wraps `Layout` in the paper, in the user's theme and padded clear of the safe-area insets like `WatchlistShell`, around `AuthColumn` (the logo above a `Card`); their views are in `src/components/auth/` (`SignInView`, `ConfirmView`, `SetPasswordView`, and `PasswordInput`, whose show/hide button stays hidden without JavaScript, as the theme switch does), on the shadcn `Input`. From lg the product page shows the same list beside the product, with its row selected, from the list page's own three reads, which ask no shop. A search by name asks for the product's brand, name and size text, each once (`nameQuery`), since a name from Natura, Hebe or Super-Pharm often holds the brand and the size already: the brand goes first only when the name doesn't start with it, and the size text last, in place of a size the name ends with (`splitTrailingSize` in `size.ts`), both compared as the name check folds words (`foldedWordsOf` in `matching.ts`); over 80 characters only the name is cut, at a word, keeping the brand and the size whole (`toShopQuery`'s `KeptText` in `search-query.ts`), unless they leave it no room. A Rossmann product's name holds neither, so its query is its brand, name and size text. The query keeps the words of the product's own shop, so a shop that writes the product otherwise may find nothing, which the lookup stores as "not found", a known limit (the owner's call of 2026-10-08, `context/foundation/test-plan.md` §7): Super-Pharm's "Maybelline Mascara Lash Sensational Sky High Cosmic Black 7.2 ml" finds nothing at Rossmann, which sells it and writes "tusz do rzęs" and "7,2 ml", and "Szukaj ponownie" sends the same query. Neither reads a search without an answer as nothing found: after an EAN search without one nothing more is asked, and the choice's name search without one marks the EAN search's candidates incomplete, or, without any, says the shop gave no answer. A decision is posted for one priced shop, whose adapter checks a confirmed candidate's id and links and the id of a match a re-pin replaces (`parseMatchForm`), and its redirect names that shop (`decisionBackTo`); the form doesn't say which shop is the product's own, so one posted for that shop is stored and counts for nothing. A product's decisions are read row by row in every priced shop (`listMatches` and `listMatchStates` in `src/lib/services/matches.ts`, by the four rules written there), and whoever reads them narrows them to the product's matched shops, as reading those shops alone would: a row of a shop outside the list, the product's own shop included, is left out, so a shop switched off again leaves its stored decisions harmless, and an odd row makes only the decisions it may be unreadable, never undecided. Pinned items' prices come from Rossmann's v2 detail by id, one product per request since no batch route is known (`fetchRossmannPrices`), from Luigi's Box filtered by item id, one repeated `f[]=<field>:<id>` per item (Natura's `sku`, Hebe's `ID`) and up to 50 per request, with `hit_fields` naming only the price attributes (`fetchNaturaPrices`, `fetchHebePrices`), and from Super-Pharm's Algolia filtered by `objectID`, `objectID:<id>` joined by OR, up to 20 per request, since a parameter's value may hold 512 bytes, retrieving only `price`, `in_stock` and `inStoreOnly` and sending `enableRules=false`, so Super-Pharm's query rules can neither hide an asked item nor add one (`fetchSuperPharmPrices`; research §2.1, §2.2, §2.3, §2.5). A pinned Rossmann product is `missing` only on Rossmann's own 404 in `application/problem+json`, as `rossmann-detail-unknown.json` recorded; any other 404, as a moved route would get, is unavailable. An id a clean answer leaves out is `missing`, as Hebe leaves out an item it no longer sells online, while a hit that can't be read or wasn't asked for, or an answer that may hold only part of its hits (a `next_page`, or a `total_hits` above the hits it holds, missing, or not a whole number of 0 or more; on Algolia, an `nbHits` other than the hits it holds, or anything but page 0 of at most one page), leaves every unanswered id unavailable. The batches, the stop after a refusal or after `FAILED_REQUESTS_BEFORE_STOP` failed requests in a row, and this rule are shared by the shops that fetch in batches (`fetchPinnedPrices` in `pinned-prices.ts`, given each shop's batch size, request and hit reader), as the value helpers are (`shop-values.ts`). `refreshPrices` (`src/lib/services/price-refresh.ts`) asks every priced shop at once through the gate, each through its fetcher one request at a time, stops asking a shop that refused at once, and one whose requests failed twice in a row (`FAILED_REQUESTS_BEFORE_STOP` in `pinned-prices.ts`, its counter's skips included, logged as "requests stopped", and an id never sent counts for nothing): a batched shop's request counts when its answer can't be read, and any answer it can read resets the count, while Rossmann, asked one product per request, counts only a request it gave no response to, one that timed out, its body included, failed on the network or that the counter's skip kept from being sent (`requestRossmannPrice`'s `responded`, `shopResponded` in `shop-outcome.ts`), so a product whose answer always fails, which stores nothing and comes first again, can't keep the list's other Rossmann items unasked, while the other shops go on, and stores each shop's answers as soon as that shop is done. A stored id is user input: a Rossmann id must be all digits (`isRossmannProductId`) before it becomes a path, because the gate checks the host, not the path, and a `..` segment would reach another path, and each Luigi's Box adapter checks an id before it goes into a filter, as Super-Pharm's does (digits only, at most 12). Two edges of the gate and the search are accepted (`context/foundation/test-plan.md` §7): a block report that fails leaves the shop on for every other path and user, while its caller still gets `blocked`, and the search schema admits any text of its characters and length, such as `../` sequences, whose effect on a shop's firewall is unknown and mustn't be probed.
- **Data**: migrations go in `supabase/migrations/` named `YYYYMMDDHHmmss_short_description.sql`, with RLS enabled on every table and per-operation, per-role policies. The production project doesn't expose new tables to the Data API automatically, so every migration also grants table privileges explicitly: to `authenticated`, and to `anon` only where that's intended. It has automatic RLS on as a safety net. A table reached only through `security definer` functions gets no grants and no policies (`shops`, `shop_requests`). A user deletes only their own `watchlist_items` row and updates none. `watchlist_matches` holds each user's private decisions, one per product and shop: `matched`, `unmatched` (the user declined) or `not_found` (the lookup found nothing); RLS lets its owner change a decision in any state, so the code narrows each write by the state it expects (`record` in `src/lib/services/matches.ts`: the lookup and a first choice only over `not_found`, a re-pin only over the decision it replaces), and the update grant covers only the decision's columns. A direct call can still set a user's own decision back to `not_found` or mark their own match `auto`, which changes only their own list. Foreign-key checks bypass RLS, so its composite foreign key `(watchlist_item_id, user_id)` ties each match to its owner's product, and its `on delete cascade`, which needs no grant, deletes a removed product's decisions, its owner's only; `watchlist_matches` has no delete grant or policy, so that's the only way a decision goes, and no observation references a product, so a removal deletes none. `price_observations` holds every price check and is append-only: RLS lets only the shop item's watchers (users with the item on their list, or a `matched` match to it) read and add rows, and no grant or policy allows an update or a delete. Its column grants leave each row's time, source and recording user to the database and keep `recorded_by` unreadable, so an insert asks for no rows back and every read names its columns. A check that finds the item gone adds a `missing` row: the last price stays, marked out of date, and can't be named cheapest. The app reads `latest_price_observations`, a `security_invoker` view of each item's last check and last price. The product page reads `price_summaries` instead, in its one price read: the same, plus each item's lowest orderable price and the Warsaw days carrying one in the 30 days before today, today excluded, for the good-price judgement. The list keeps the lighter view. A row whose history can't be read keeps its price, with no history to judge by, so the product page prices a shop the list prices. Accepted risks, to revisit before inviting more people: with no server-only key, a user can add a plausible fake price for any item, since watching one is self-service, and it counts as the item's last check, so its watchers' automatic refresh waits up to 15 minutes, and it steers the good-price judgement: a fake low price becomes the item's history low for 30 days, the table being append-only, so every co-watcher with enough history sees „Zwykła cena”, and a fake high 30-day low on the latest check stamps „Dobra cena!” until the next check; people watching the same item see each other's check times; a stale form whose decision has the newer decision's content still lands, since its `replaces` names a state and an item, not a version (the ABA case); and the table-wide insert grants let a caller choose a row's id, so someone who knows a product's UUID could learn from a duplicate-key error whether it exists (`context/foundation/test-plan.md` §7). The length and format checks on `watchlist_items` and `watchlist_matches` mirror `PRODUCT_LIMITS`, and the bounds on `price_observations`' price, regular price and 30-day low mirror `PRICE_LIMITS` (both in `src/lib/services/product-limits.ts`), so changing a limit needs a migration too. Postgres lets `PUBLIC` execute every new function, so revoke that from `public, anon` and grant `execute` to `authenticated` explicitly. The one exception is `applied_migrations()`, which only `anon` may execute, for the deploy gate, since its answer is the versions of the repository's public migration files. `auto_expose_new_tables = false` in `supabase/config.toml` gives the local stack the same grants as production, so a missing grant fails locally and in CI first. A new view still came with a privilege for `anon` on the local stack (2026-10-07), so a view's migration revokes it, as both views' do, and `scripts/check-catalog-db.mjs` fails on any privilege of `anon` in `public` but EXECUTE on `applied_migrations()`. Migrations reach production only when the owner runs `npx supabase db push`, after a one-time `npx supabase login` and `npx supabase link --project-ref <ref>`; never `supabase config push`. Before its merge, a migration file exists only on its pull request's branch, so the owner pushes it from a checkout of that branch: from `main`, the push finds nothing new and sends nothing. After the owner's push, confirm it with `npx supabase migration list --linked` (read-only): the new migration must show a remote version before the PR that needs it merges; a dashboard check isn't enough on its own. The deploy gate enforces it: a checked deploy refuses while any migration file isn't applied, and `node scripts/check-migrations-applied.mjs` confirms a push too. If production answers PGRST205 ("Could not find the table … in the schema cache"), check that list before reloading the schema cache. Shared types (entities, DTOs) belong in `src/types.ts` and business logic in `src/lib/services/`.

## Tooling and repository conventions

- Pre-commit (husky + lint-staged) runs `eslint --fix` on `*.{ts,tsx,astro}` and `prettier --write` on `*.{json,css,md}`; a lint error blocks the commit.
- Claude Code hooks (`.claude/settings.json`, scripts in `.claude/hooks/`) check the agent's work while it goes. After each Write or Edit, ESLint lints that one file, without `--fix`. At the end of a turn, ESLint lints every changed or new code file, and the whole Vitest suite and `astro check --noSync` run; a failure sends the agent back once (`stop_hook_active`). New untracked files count only in the root, `src/`, `scripts/`, `tests/` and `supabase/`, and a tree that already passed is skipped (`node_modules/.cache/claude-hooks/`). They add to the git hook and CI, and replace neither.
- Prettier uses 120 columns and sorts Tailwind classes; let it reorder them.
- `.nvmrc` pins Node 24.18.0 (npm 11.16.0), and both CI and Workers Builds read it. Change dependencies with that npm. npm 11.6.2 writes lockfiles without the `@emnapi/*` entries that `npm ci` in npm 10.9 and 11.16 requires, so CI fails at install. Local Node below 24.16 prints non-fatal `EBADENGINE` warnings from `eslint-plugin-astro` at install.
- CI (`.github/workflows/ci.yml`) runs on pushes and PRs to `main`: lint, `astro check`, unit tests and build in the `ci` job; the shop gate, watchlist, shop matches, price observations and catalogue database checks, the database tests (`npm run test:db`), the smoke test and the two-user check against a local Supabase in the `smoke` job; and the Playwright e2e suite on the production preview, against a local Supabase of its own, in the `e2e` job. It never deploys and needs no repository secrets; keep Cloudflare tokens and Supabase keys out of GitHub. The `smoke` job also runs the production check against the preview and the deploy gate against the local stack, each passing and failing where it must. The `Deploy check` workflow (`.github/workflows/deploy-check.yml`) runs on each push to `main`: it waits for the commit's `Workers Builds` check and fails when the build is red, so GitHub emails whoever merged; it reads only check runs, with its own read-only `GITHUB_TOKEN`, and prints no link, since a check's link carries the Cloudflare account id.
- `context/` is the 10x workflow surface: `foundation/` living docs are edited in place, `changes/<id>/` holds per-change artefacts created with `/10x-new`, and `archive/` is read-only (see @context/foundation/README.md).
- The 10x CLI (`npx @przeprogramowani/10x-cli@latest`) manages `.claude/`, `.10x-cli.json` and the course block at the bottom of this file, and tracks them by content hash. `.prettierignore` and `.gitattributes` (LF everywhere) keep them byte-identical, so never reformat them. Apply a lesson's course block with `get <lesson> --type rules`: in CLI 1.25.2 a plain `get` removes the block. After any `get` or `sync`, check that the block is still there and re-apply it if not. On Windows the CLI's manifest write sometimes fails with `EPERM` (the file is briefly locked), and some runs print nothing; rerun the same command.
- `CLAUDE.md.scaffold` is the starter's original rules file left by the bootstrap merge and `context/changes/bootstrap-verification/verification.md` is its audit log; Claude Code loads neither.
- Changes reach `main` only through pull requests. The `preventFailedDeploy` ruleset requires green `ci`, `smoke` and `e2e` checks, and every merge deploys to production through Workers Builds, so open the PR and leave the merge to the owner.
- The default branch is `main` of a public GitHub repository: never commit account IDs, emails, the workers.dev subdomain or key values. There is no enforced commit convention yet.

## 10xDevs AI Toolkit - Module 4, Lesson 1 (Context at Scale)

Keep this rules file lean and point from it to the context that lives elsewhere. A large codebase does not need a larger root file.

```
lean root rules file -> context/ (system of record) -> per-module rules only when a trigger signal appears
```

| Skill | Use it when |

| `/10x-lesson` | An agent mistake that keeps coming back should become a recorded lesson, not another line in this file. |

### Hard rules

- **Instruction files add up; they don't override.** Tools merge the root, nested and user-level files. Don't repeat the same rule at several levels.
- **The inclusion test.** A line belongs here only if the agent would get it wrong without it. Facts the agent can read from the code or from `context/` stay there and get a pointer.
- **Add per-module structure only when a signal shows up.** Examples: the agent keeps confusing two areas, or one module's conventions crowd out everything else. Repo size alone is not a signal.
