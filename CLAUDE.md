# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Drogeria Radar: a private, invite-only web app for a handful of users that shows which of five Polish drugstore chains (Rossmann, Hebe, Super-Pharm, dm, Drogerie Natura) sells a repeat-purchase product cheapest today, with regular and promo price, the Omnibus 30-day low and the age of every price. Astro 7 SSR, React 19 islands, Tailwind 4 and Supabase (Postgres, auth, RLS) on Cloudflare Workers, bootstrapped from `10x-astro-starter` on 2026-09-20. No starter page remains: `/` (`src/pages/index.astro`) sends a signed-in user to `/watchlist` and a visitor to `/auth/signin`.

## Non-negotiables

- Sign-up is invite-only with no open registration (PRD FR-001): the app has no sign-up page or route and sends no email, and a person gets an account only from the owner, made in the Supabase dashboard or through an invite or recovery link the owner makes with `scripts/owner-link.mjs`. `[auth] enable_signup = true` in `supabase/config.toml` is there only so the local tests can sign throwaway users up through Auth; `[auth.email] enable_signup` is the whole email provider, which password sign-in needs, so it stays on everywhere. The production Supabase project has "Allow new users to sign up" off; never run `supabase config push` against it, because that pushes `enable_signup = true`. A secret key (`sb_secret_…`, or the legacy `service_role` JWT) bypasses RLS and is the owner's alone, for one `owner-link.mjs` run in their own shell: never put one into the app, the Worker, `.env`, `.dev.vars` (which the build copies into `dist/server/`), CI or a test.
- Watchlists are private per user; price observations are shared by everyone who watches the same shop item and hidden from everyone else (FR-005), so no one can list what others watch. Enforce this with RLS policies, not only with query filters. Removing a product deletes the user's own watchlist row and, through the cascade, their decisions for it, never an observation.
- Every displayed price shows its source and fetch time (FR-010, FR-011). A failed fetch shows the last known price with its age or a visible gap, never a blank, a zero or a silently stale value. Online prices are labelled as online; never claim shelf prices.
- Shop fetches run server-side and on demand (FR-008), under a per-shop request cap for the whole deployment, and stop for a shop that blocks or asks. Never circumvent bot protection; Sephora, Douglas and Notino are excluded for that reason. dm is out of the MVP for the same reason: its search refuses Cloudflare Workers traffic (research §9), so don't build a dm adapter or a proxy for it.
- Every shop request goes through `gate.fetch` from `src/lib/services/shop-gate.ts`; never call `fetch` on a shop host directly, and add a new host to `SHOP_HOSTS` before calling it. The gate allows `public.shops.cap_per_minute` requests per shop (30 by default) in any 60 seconds, never follows redirects, pauses a shop after a 429 or a 503 with Retry-After, and stops it after a 403 or a bot challenge until the owner sets `enabled` back to true in `public.shops`. It needs the signed-in user's Supabase client (`shopGateFor(supabase)`): without one, every call is skipped as `unavailable`. Callers read an `ok` body promptly, because the gate's 8 s timeout covers the body too, and show a read error as a gap. Lookup tests assert which URLs the replay fetch served, because a miss looks like `failed/network`. User search text is validated with zod, for allowed characters and length, before it goes into a shop URL, because one 403 stops the shop for everyone.
- The confirmed per-shop item is the anchor and EAN only a helper (FR-004, FR-006): one EAN can come with another size in another shop (Hebe's 5,5 ml lip balm carries the EAN of Rossmann's 4,8 g one), Hebe's size field `Pojemność` is unreliable (the "wrong EAN" once reported for Hebe was that field, research §2.2), and Super-Pharm's search index has no EAN.
- Read `SUPABASE_URL` and `SUPABASE_KEY` only through `astro:env/server` (declared in `astro.config.mjs` as optional server secrets), never `import.meta.env`.
- The HTML-comment-delimited lesson block at the bottom of this file belongs to the 10x CLI and is replaced on every `npx @przeprogramowani/10x-cli get <lesson> --type rules`. Project rules live above it; never edit inside it.

## Commands

Prerequisite: copy `.env.example` to both `.env` (Node processes: build, check, smoke) and `.dev.vars` (the Cloudflare dev runtime) and fill in the two Supabase values. Without them the app still runs, but auth is disabled and every page shows an error banner.

- `npm run dev` — dev server on the Cloudflare workerd runtime at http://localhost:4321. Under an AI agent, `astro dev`, like `--background`, backgrounds the server and kills it if it isn't ready within 30 s, and a start after `astro sync`, `astro check` or `npm run build` takes longer: they invalidate Vite's dependency cache. So start `ASTRO_DEV_BACKGROUND=1 npx astro dev` as a background task, which skips the agent detection and its limit; `npx astro dev stop` still stops it. If the first start after that crashes with "The file does not exist at …node_modules/.vite/deps_ssr/…", start it again.
- `npm run build` / `npm run preview` — production build via `@astrojs/cloudflare`; preview serves `dist/` on workerd. The build copies `.dev.vars` into `dist/server/`, so rebuild after changing it. Preview keeps running as a background server, and a second `npm run preview` silently reuses it; run `npx astro preview stop` before rebuilding.
- `node scripts/check-built-fonts.mjs` — checks that the build shipped its web fonts, which `astro build` downloads from Google Fonts: a build that can't reach them still succeeds, with only a warning and no font files. `npm run build` runs it after `astro build`, so such a build fails wherever it runs: in CI, in Workers Builds, which then deploys nothing, and locally, offline too.
- `npm run lint` / `npm run lint:fix` / `npm run format` — ESLint (type-checked rules with the Astro and React plugins) and Prettier.
- `npx astro sync && npx astro check` — generate `.astro/types.d.ts`, then type-check `.astro` and TS files. CI runs both. On a fresh checkout run `astro sync` before `lint` or `check`; both depend on the generated types. While a dev server runs, type-check with `npx astro check --noSync`: the sync rewrites Vite's SSR dependency cache (`node_modules/.vite/deps_ssr`), and the running server then answers 500 on every page until it restarts.
- `npm run smoke` — dependency-free auth-flow smoke test (`scripts/smoke.mjs`) against a running server, `BASE_URL` defaulting to localhost:4321. It reads `SUPABASE_URL` and `SUPABASE_KEY` from `.env` (`node --env-file-if-exists=.env`) and refuses any Supabase but the local stack, because it signs its throwaway user up through Auth's own `/auth/v1/signup` (local sign-up on, email confirmation off). It pins the front door's redirects and return paths, the auth routes' codes and origin refusals, the confirm and set-password contracts and the removed pages' 404s, with no secret key and no shop request.
- `npm run test` — Vitest over `src/**/*.test.ts`, in Node rather than workerd; CI runs it in the `ci` job. Run one test with `npx vitest run <file> -t "<name>"`. Tests never reach live shops: they serve recorded responses through `createReplayFetch` (`src/lib/services/testing/replay-fetch.ts`). Shop fixtures live in `src/lib/services/shops/fixtures/`: real answers recorded once with `curl` using the gate's User-Agent, at least 2 seconds apart, never from CI.
- `node scripts/check-shop-gate-db.mjs` — checks the shop gate's SQL functions, RLS and grants against the local Supabase; CI runs it in the `smoke` job. It needs `npx supabase start` and the local stack's URL and anon key in `SUPABASE_URL` and `SUPABASE_KEY`. Its rows persist, so run `npx supabase db reset --local` before a rerun. A reset also deletes every local user, including the owner's own test account, so say so before running it; the app has no sign-up page, so recreate that account afterwards in local Studio (Authentication → Users → Add user, with Auto Confirm User) or with an `owner-link.mjs` invite link.
- `node scripts/check-watchlist-db.mjs` — proves with two throwaway users that watchlist rows stay private to their owner, can't be changed and are removed only by their owner, after which the same product can be added again (RLS and grants); CI runs it in the `smoke` job. It needs the same local stack and variables, and signs up fresh users each run, so reruns need no reset.
- `node scripts/check-matches-db.mjs` — proves with two throwaway users that shop matches stay private to their owner, attach only to the owner's own products, change in any state only through their owner and never to another product, user or shop, and are deleted only with their product, and that `watchlist_items` and `watchlist_matches` refuse values outside their bounds; CI runs it in the `smoke` job. It needs the same local stack and variables and, like the watchlist check, signs up fresh users each run, so reruns need no reset.
- `node scripts/check-prices-db.mjs` — proves with two throwaway users that only a shop item's watchers read and add its price observations, the view included, that no one can change or delete one or set its time, source or recording user, that removing a product deletes none, so the item's other watchers keep its prices and the remover no longer reads or adds them, and that a re-pin changes which item a user watches; it also checks S-03's EAN and match-update rules on the watchlist tables. CI runs it in the `smoke` job. It needs the same local stack and variables, and each run uses fresh users and shop item ids, so reruns need no reset and no real product gets a test price.
- `npx playwright test` — the Playwright e2e suite in `tests/e2e/`: Chromium at 390 × 844 with touch, against the workerd production preview, which the config builds and starts on 4321 (`E2E_PORT` overrides it); one spec with `npx playwright test tests/e2e/<name>.spec.ts`. It needs Docker, `npx supabase start` and the local stack in `.env` and `.dev.vars`, and the config refuses any other Supabase, because a run stops every enabled shop of the deployment it talks to. Each run signs up a throwaway local user through Auth, signs it in once through the Polish sign-in form ("E-mail", "Hasło", "Zaloguj się"), and holds every enabled shop under its own name: it refuses to start while another run or a manual `stop` holds them, switches back on only its own, also after Ctrl+C, and fails if a shop request was reserved meanwhile. It never reuses a server already on its port, so stop one there first (`npx astro dev stop`, `npx astro preview stop`) or set `E2E_PORT`. Give the command a timeout of several minutes, or run it in the background: a run killed outright leaves its shops stopped, and the next run refuses until `node scripts/e2e-local-db.mjs restore`. Never pass `--no-deps`, which skips the shop stop. Between runs, `node scripts/e2e-local-db.mjs stop` and `restore` hold the shops while you explore the app with playwright-cli; `restore` releases every e2e hold, so use it only while no run is going. How to add a spec is in `context/foundation/test-plan.md` §6.3. CI runs the suite in the `e2e` job.
- `npx supabase start` / `npx supabase stop` — local Supabase via Docker (API on 54321, Studio on 54323, settings in `supabase/config.toml`). Apply new migrations to the running stack with `npx supabase migration up --local`: unlike `db reset --local`, it keeps local users. Never run `migration up --linked`, which would apply them to production.
- `SUPABASE_URL=<project URL> SUPABASE_SECRET_KEY=<sb_secret_… key> APP_URL=<app origin> node scripts/owner-link.mjs <invite|recovery> <email>` — the owner's link for a person: an invite gives a new account its first password, a recovery a new one. Only the owner runs it, on their own machine, with the secret key in that one command's environment. It asks Auth's admin `generateLink`, which sends no email, and prints only `<APP_URL>/auth/confirm?token_hash=…&type=…` on stdout, the format `confirmFormSchema` takes. A link works once, for the Email OTP Expiration (86400 s, so 24 hours, with a 10-digit code: `otp_expiry` and `otp_length` under `[auth.email]` locally, which a running stack reads after `npx supabase stop` and `npx supabase start`, and the dashboard on production), and a newer link of the same type for the same email replaces it. The script refuses bad input, a key that isn't secret and an `APP_URL` with a path before any request, and on a refusal prints only Auth's code with a hint: `email_exists` (make a recovery link) or `user_not_found` (make an invite link). Locally the key is `SECRET_KEY` from `npx supabase status -o env` and `APP_URL` is `http://localhost:4321`; production's steps, and the read-only check that production still refuses sign-up, are in `context/deployment/deploy-plan.md` ("Accounts and links (S-07)").
- Production deploys by merging to `main`: Cloudflare Workers Builds runs `npm run build` and `npx wrangler deploy` for the Worker `drogeria-radar`. A manual `npx wrangler deploy` is for emergencies only, from a clean `main` after `npm run build`. Set secrets with `npx wrangler secret put SUPABASE_URL --name drogeria-radar` and the same for `SUPABASE_KEY`. What is live, and how to roll back: `context/deployment/deploy-plan.md`.

## Architecture

- **Request lifecycle**: `output: "server"`, so every page and API route renders on demand. `src/middleware.ts` runs on each request: it builds the request's only Supabase client and keeps it in `Astro.locals.supabase`, stores the user in `Astro.locals.user` (both typed in `src/env.d.ts`) and redirects unauthenticated requests whose path starts with an entry of `PROTECTED_ROUTES` to sign-in: the list's or a product's page with itself as the way back, keeping only the list's filter (`signInHref(returnPathFor(url))`, such as `/auth/signin?next=%2Fwatchlist%2F<id>`), any other path, the API routes and `/auth/set-password` included, to the plain `/auth/signin`, which the product's island reads as an ended session. Gate new pages by adding them there. Pages and routes use `locals.supabase` and never create a second client: `@supabase/ssr` sends its cache headers when it writes auth cookies, and only the middleware's client carries them to the response. Every signed-in response is `Cache-Control: private, no-store`.
- **Null-client contract**: `createClient()` in `src/lib/supabase.ts` returns `null` when the env is missing, and `locals.supabase` is then null; the middleware, `/`, the auth pages and API routes (`/auth/signin`, `/auth/confirm`, `/auth/set-password`, `/api/auth/signin`, `/api/auth/signout`, `/api/auth/confirm`, `/api/auth/set-password`), the watchlist pages and routes (`/watchlist`, `/watchlist/<id>`, `/api/watchlist`, `/api/watchlist/matches`, `/api/watchlist/prices`, `/api/watchlist/refresh`, `/api/watchlist/remove`) and `src/lib/config-status.ts` (rendered as a banner by `src/layouts/Layout.astro`) all tolerate that. New Supabase code keeps this contract unless the contract is removed deliberately everywhere.
- **API routes**: `src/pages/api/**` export uppercase handlers (`export const POST: APIRoute`). A form route takes a plain HTML form post, which Astro's `checkOrigin` refuses from another site, guards `formData()`, validates the form with zod via `import { z } from "astro/zod"` (no extra dependency) and redirects back with an error code that the page maps to its own text (`src/lib/notices.ts`, where a code the app didn't send shows nothing), never a message, so a crafted link can't put words on the page: `/api/watchlist` and the auth routes do, the latter reading only an Auth error's `code` and `status` (`authErrorCodeOf`, `confirmErrorCodeOf` and `passwordErrorCodeOf` in `src/lib/services/auth.ts`). Reuse this shape for new forms. A JSON route, such as `/api/watchlist/prices`, accepts only `application/json` and refuses other sites itself with `refuseJsonRequest` (`src/lib/json-request.ts`), because Astro's `checkOrigin` refuses cross-site posts of form content types only.
- **Sign-in and links**: the auth pages are plain Astro forms in Polish that work without JavaScript and ask no shop; their rules (the zod schemas, Auth's errors as codes, each redirect) are in `src/lib/services/auth.ts` and their texts in `notices.ts`. A sign-in goes back to `returnPathOf(next)` (`src/lib/services/return-path.ts`): only `/watchlist` or `/watchlist/<uuid>` with at most a chip's `?f=`, anything else being `/watchlist`, because the landing counts as the user's own navigation, so a `next` carrying `repin`, `retry` or `q` would spend the shops' cap. A signed-in user opening `/auth/signin` goes there too. `signInHref`, beside `SIGN_IN_PATH` and `NEXT_PARAM` in the browser-safe `watchlist-rows.ts`, builds the link to sign-in with its way back, for the middleware and the island's "Zaloguj się ponownie". Sign-out ends this device's session only (`signOut({ scope: "local" })`) and lands on `/auth/signin?signed-out=1` ("Wylogowano."), a failed one on the list with its notice. An owner's link opens `/auth/confirm?token_hash=…&type=invite|recovery`, which only renders "Ustaw hasło", so a link preview can't use it up: only the button's post calls `verifyOtp` (on `locals.supabase`), and the page sends `no-store` and `Referrer-Policy: strict-origin`, not `no-referrer`, under which the browser would post its form with `Origin: null`, which `checkOrigin` refuses. `/auth/set-password` and its route accept only a session a link opened within the last 60 minutes (`linkSessionOf` on `getClaims()`'s `amr`) and send any other, a password sign-in's included, to the list before any update, so there's no change-password page; a new password has 8 to 72 UTF-8 bytes and lands on the list with "Hasło zapisane.".
- **Workers constraints**: requests are short-lived and the runtime is workerd with `nodejs_compat`, not full Node. The post-MVP daily refresh (FR-015) needs a Cron Trigger or a queue, not a request handler.
- **UI**: `/watchlist` is the main screen, and the app's text is Polish (`Layout`'s default `lang="pl"`). `/watchlist/<id>` is a product's page, which "Dodaj" and each list entry lead to. Both stand on `src/layouts/WatchlistShell.astro`, which wraps `Layout` in the dotted paper (`bg-paper`): from lg (1024 px) a header on top (`AppHeader.astro`: the logo, the search with its `/` shortcut, the theme switch, the account, its email from xl, and "Wyloguj"), the list in a 420 px column on the left (the `head`, `rows` and `footer` slots, the rows scrolling on their own) and the main pane (the default slot), which scrolls on its own; below lg a phone's screen, where the list's header is the logo and the account menu (`AccountMenu.astro`, a `<details>` that opens without JavaScript) and a product has its own row back to the list. The shell opens with a skip link to its `<main>` ("Przejdź do listy", "Przejdź do produktu"), shown only while it has the focus, and names the list beside a product by the list's heading (`listHeadingId`). The shell's pieces are in `src/components/shell/` (`AppHeader`, `AccountMenu`, `SearchForm`, `ThemeToggle`, `LogoMark`) and the list's in `src/components/watchlist/` (`ListHead` with the list's "Odśwież ceny", `FilterChips`, `ListRows` of `WatchlistRow`s with their `RowTag` price tags, `ListFooter` and `SearchResults`). The auth pages (`/auth/signin`, `/auth/confirm`, `/auth/set-password`) stand on `src/layouts/AuthShell.astro`, which wraps `Layout` in the paper, in the user's theme and padded clear of the safe-area insets like `WatchlistShell`, around `AuthColumn` (the logo above a `Card`); their views are in `src/components/auth/` (`SignInView`, `ConfirmView`, `SetPasswordView`, and `PasswordInput`, whose show/hide button stays hidden without JavaScript, as the theme switch does), on the shadcn `Input`. From lg the product page shows the same list beside the product, with its row selected, from the list page's own three reads, which ask no shop. What a list row says (its tag, with the tag's price's shop and age on the line under it, whether the chips `?f=promo` and `?f=check` hold it, the chips' counts and links, and its screen-reader line) is decided in the browser-safe `src/lib/services/watchlist-rows.ts`, which reads each matched shop's state on its own (`matchStatesOf`) and words the list's alert and footer (`matchesFailedText`, `priceSourcesText`, joined "a, b i c" by `listJoin` in `price-comparison.ts`), and what a product's prices come to in one verdict (unread, cheapest, only, unavailable, stale or none) in `verdictOf` in `src/lib/services/price-comparison.ts`, which the list's tag, the product's hero and the selected row's live tag all use. Freshness and the cheapest shop are decided only in `price-comparison.ts` (stale after 24 hours; only fresh prices orderable online can win). Without a stored decision in a matched shop, the product page looks the product up there, with `?repin=<shop>` it looks that shop's stored match or decline up again for the user to change it, and with `?retry=<shop>` that shop's stored "not found" (`decideMatchStep`, `repinShopOf` and `retryShopOf` in `src/lib/services/match-step.ts`), but, like the search, only on the user's own navigation (`isOwnNavigation`), so a link from another site can't spend the cap everyone shares, and a page opened to re-pin or retry one shop looks up no other: a shop there without a decision only offers its button; Astro's prefetch stays off for the same reason, since its fallback fetch sends no `Sec-Purpose` header. `runMatchSteps` in `src/lib/services/shop-matching.ts` runs the page's step for every matched shop at once, each shop's searches and writes one after the other, and settles each shop on its own, so one whose step throws shows as unavailable beside the others. The product area, from the title row down, is the React island `src/components/watchlist/PriceComparison.tsx`, which `PriceComparisonView.tsx` renders from `ProductTitle`, `VerdictHero` with its `Sticker`, `PriceTrack`, `ShopCard`, `MatchCard`, a phone's bottom bar (`RefreshBar`) and the refresh buttons' `RefreshForm`, while what they say is decided in `price-comparison-state.ts` (`heroOf`, `trackOf`, `trackHint`, `checkedCaption`, `verdictOfState`) and each matched shop's card in `match-card.ts` (`matchCardOf`). The island shows the stored prices at once and, again only on the user's own navigation and never while a re-pin's choice is open (`autoRefreshOf` in `src/lib/services/match-step.ts`), refetches each shop last checked more than 15 minutes ago through `/api/watchlist/prices`, one request per shop naming the shop item the page shows, so each card updates as its shop answers, and a page left open after a re-pin elsewhere gets `changed` (409) and asks for a reload instead of showing another item's price; after each change of its rows it sends `PRICES_EVENT` on `window`, which the selected row's `RowTag`, an island there that hydrates only from lg (`client:media`), follows. Each shop appears once, in its card: a matched shop's says where its matching stands and shows its own decision's notice or error, which reach that card through the shop the address names (`SHOP_PARAM`; `decisionNotice` and `decisionError` in `src/lib/services/match-view.ts`), though only the decline's text names the shop, and below the island one `MatchChoice.astro` for each shop with candidates waiting holds only that shop's choice among them, a first lookup's or a re-pin's. That choice marks the current item "Obecne dopasowanie", where an automatic match can still be confirmed ("To ten produkt"), offers "Żaden z nich" only from a match and ends with "Anuluj", and each of its forms posts the decision it replaces (`replaces`), so one from a stale tab changes nothing and says the decision was already stored. `RemoveProduct.astro`, last on the product's page at every width, is a `<details>` whose confirm opens in place without JavaScript and posts to `/api/watchlist/remove`, which asks no shop; a failed removal comes back to it, open with its error (`removalBackTo` in `src/lib/services/watchlist.ts`), or, when the product is gone after all, to a not-found page that says it's no longer on the list. The stickers state facts only, "Tylko 1 sklep" and "Stara cena", until FR-012 (S-04) judges a price. The list shows stored prices only and asks no shop; its "Odśwież ceny" posts to `/api/watchlist/refresh` with the list's filter and, beside a product, the product's id, which `listRefreshBackOf` validates before any refresh (a crafted id refreshes nothing), and `listRefreshBackTo` sends it back there with the list's own notice parameter, `LIST_PRICES_PARAM`; a product's "Odśwież ceny", which posts to the same route without JavaScript, comes back with `PRICES_PARAM` (`productRefreshBackTo`). The refresh's codes are `PRICE_REFRESH_CODES` in `src/lib/services/price-refresh.ts`, with `listRefreshBackOf`, `listRefreshBackTo` and `productRefreshBackTo`, and the notice parameters and the texts each page shows for them, like a decision's (with its shop), "Dodaj"'s and a removal's, are in `src/lib/notices.ts`, whose `withoutNotices` makes both pages' address bars forget theirs once shown (`NOTICE_PARAMS`, `LIST_NOTICE_PARAMS`), keeping the list's filter; the product page's also forgets `?repin=<shop>` (`REPIN_PARAM`) once the choice has rendered, so going back to it asks the shop nothing, and a retry (`RETRY_PARAM`) that stored its outcome redirects to the plain address. `islandConfig` in `eslint.config.js` lists every module the islands load (their pieces and rules, `watchlist-rows.ts`, `price-comparison.ts`, `src/lib/services/matching.ts`, `src/lib/shop-messages.ts`, `src/lib/json-request.ts`, `notices.ts`, `src/lib/theme.ts`, `src/lib/utils.ts` and the shadcn components) and refuses server-only imports there, with `@/lib/services/matching`, `@/lib/services/price-comparison` and `@/lib/services/watchlist-rows` the only services it admits, so a module an island starts to import joins its `files`. - **Shops and matching**: product search is Rossmann's, through `src/lib/services/shops/rossmann.ts`, and each watched product is matched once in each matched shop: `MATCHED_SHOPS` in `src/lib/services/price-comparison.ts` (Natura, then Hebe), the only switch for what the pages, routes, schemas, the island and the list use. `MATCHABLE_SHOPS` beside it names every shop the code can match, switched on or not, and keys the per-shop tables with Rossmann (`KnownShop`): the labels (`SHOP_LABELS`), the adapters (`SHOP_ADAPTERS` in the server-only `src/lib/services/shops/registry.ts`) and the price fetchers (`PRICE_FETCHERS`, taken from the registry); every rule that takes a list of shops defaults to the switched-on ones (`MATCHED_SHOPS`, or `PRICED_SHOPS` with Rossmann), so a test can pass a shop that isn't switched on. A new shop joins `MATCHABLE_SHOPS` with its label and its registry entry, then `MATCHED_SHOPS`, where the compiler asks for its colour (`SHOP_FILLS`), and its adapter's tests follow `context/foundation/test-plan.md` §6.4. Natura and Hebe both search through Luigi's Box (`natura.ts` and `hebe.ts` in `src/lib/services/shops/`), on one client (`createLuigisBoxClient` in `luigis-box.ts` there) bound to each shop and its tracker, so every request is charged to the shop whose tracker it asks, and each adapter maps only its own attributes. Their tracker ids are the constants `NATURA_TRACKER_ID` and `HEBE_TRACKER_ID`: when Luigi's Box answers 404 `Catalog for tracker_id: "…" not found` (logged as "tracker id rejected", naming the constant), take the new id from the shop's own page or script (research §2.5, §2.2) and update the constant and that shop's tests' expected URLs, which pin it. Hebe's adapter offers only items Hebe sells online, because a pinned refresh never returns one it doesn't: a search leaves an item with `searchable: [false]` out, as it does a query suggestion, while a `searchable` other than `[true]` or `[false]` makes the hit unreadable, so a search whose items all read that way fails instead of finding nothing. Hebe's size is the one its legal name (`Nazwa wymagana przez prawo`), else its short description, ends with (`trailingSizeText` in `src/lib/services/size.ts`), never `Pojemność`; its price is the sale price while there is one, and orderable online means `online_flag`, never `availability` (research §2.2), where a flag that isn't a yes or a no reads as not orderable and is counted in a log line. The matching rule lives in `src/lib/services/matching.ts`: exactly one candidate that shares an EAN and the size with the product and whose brand doesn't differ is accepted automatically; otherwise the user picks among the candidates or declines them all. Two brands agree when, each decomposed (NFKD) without its combining marks, in Polish lower case and with only its letters and digits, one starts with the other (`brandsAgree`: "NIVEA" agrees with "nivea" and "NIVEA MEN", "Dr Irena Eris" differs from "IRENA ERIS"); a brand missing or blank on either side says nothing, so only one that definitely differs stops an automatic match or flags a candidate ("Inna marka"). A stored match warns of its size or brand only when both sides are known and differ (`matchDifferences`), and the list counts such an automatic match, in any matched shop, in "Do sprawdzenia", naming why on its row's screen-reader line (`matchStatesOf` in `watchlist-rows.ts`), never one the user confirmed after seeing its flags. A first lookup (`lookupInShop` in `src/lib/services/shop-matching.ts`, through the shop's adapter) searches by name only when the EAN search finds nothing; the re-pin's choice (`lookupChoicesInShop`) runs the EAN search, then the name search, since the EAN search can return another product, and offers every candidate, each item once, the EAN search's first, at most 6, accepting none on its own. Neither reads a search without an answer as nothing found: after an EAN search without one nothing more is asked, and the choice's name search without one marks the EAN search's candidates incomplete, or, without any, says the shop gave no answer. A decision is posted for one matched shop, whose adapter checks a confirmed candidate's id and links and the id of a match a re-pin replaces (`parseMatchForm`), and its redirect names that shop (`decisionBackTo`). A product's decisions are read row by row (`listMatches` and `listMatchStates` in `src/lib/services/matches.ts`, by the four rules written there): a row of a shop outside the list is left out, so a shop switched off again leaves its stored decisions harmless, and an odd row makes only the decisions it may be unreadable, never undecided. Pinned items' prices come from Rossmann's v2 detail by id, one product per request since no batch route is known (`fetchRossmannPrice`), and from Luigi's Box filtered by item id, one repeated `f[]=<field>:<id>` per item (Natura's `sku`, Hebe's `ID`) and up to 50 per request, with `hit_fields` naming only the price attributes (`fetchNaturaPrices`, `fetchHebePrices`; research §2.1, §2.2, §2.5). An id a clean answer leaves out is `missing`, as Hebe leaves out an item it no longer sells online, while a hit that can't be read or wasn't asked for, or an answer that may hold only part of its hits (a `next_page`, or a `total_hits` above the hits it holds or missing), leaves every unanswered id unavailable. `refreshPrices` (`src/lib/services/price-refresh.ts`) asks every priced shop at once through the gate, each through its fetcher one request at a time, stops asking only the shop that refused, and stores each shop's answers as soon as that shop is done. A stored id is user input: a Rossmann id must be all digits before it becomes a path, because the gate checks the host, not the path, and a `..` segment would reach another path, and each Luigi's Box adapter checks an id before it goes into a filter.
- **Data**: migrations go in `supabase/migrations/` named `YYYYMMDDHHmmss_short_description.sql`, with RLS enabled on every table and per-operation, per-role policies. The production project doesn't expose new tables to the Data API automatically, so every migration also grants table privileges explicitly: to `authenticated`, and to `anon` only where that's intended. It has automatic RLS on as a safety net. A table reached only through `security definer` functions gets no grants and no policies (`shops`, `shop_requests`). A user deletes only their own `watchlist_items` row and updates none. `watchlist_matches` holds each user's private decisions, one per product and shop: `matched`, `unmatched` (the user declined) or `not_found` (the lookup found nothing); RLS lets its owner change a decision in any state, so the code narrows each write by the state it expects (`record` in `src/lib/services/matches.ts`: the lookup and a first choice only over `not_found`, a re-pin only over the decision it replaces), and the update grant covers only the decision's columns. A direct call can still set a user's own decision back to `not_found` or mark their own match `auto`, which changes only their own list. Foreign-key checks bypass RLS, so its composite foreign key `(watchlist_item_id, user_id)` ties each match to its owner's product, and its `on delete cascade`, which needs no grant, deletes a removed product's decisions, its owner's only; `watchlist_matches` has no delete grant or policy, so that's the only way a decision goes, and no observation references a product, so a removal deletes none. `price_observations` holds every price check and is append-only: RLS lets only the shop item's watchers (users with the item on their list, or a `matched` match to it) read and add rows, and no grant or policy allows an update or a delete. Its column grants leave each row's time, source and recording user to the database and keep `recorded_by` unreadable, so an insert asks for no rows back and every read names its columns. A check that finds the item gone adds a `missing` row: the last price stays, marked out of date, and can't be named cheapest. The app reads `latest_price_observations`, a `security_invoker` view of each item's last check and last price. Accepted risks, to revisit before inviting more people: with no server-only key, a user can add a plausible fake price for any item, since watching one is self-service, and it counts as the item's last check, so its watchers' automatic refresh waits up to 15 minutes; and people watching the same item see each other's check times. The length and format checks on `watchlist_items` and `watchlist_matches` mirror `PRODUCT_LIMITS`, and the price bound on `price_observations` mirrors `PRICE_LIMITS` (both in `src/lib/services/product-limits.ts`), so changing a limit needs a migration too. Postgres lets `PUBLIC` execute every new function, so revoke that from `public, anon` and grant `execute` to `authenticated` explicitly. `auto_expose_new_tables = false` in `supabase/config.toml` gives the local stack the same grants as production, so a missing grant fails locally and in CI first. Migrations reach production only when the owner runs `npx supabase db push`, after a one-time `npx supabase login` and `npx supabase link --project-ref <ref>`; never `supabase config push`. After the owner's push, confirm it with `npx supabase migration list --linked` (read-only): the new migration must show a remote version before the PR that needs it merges; a dashboard check isn't enough on its own. If production answers PGRST205 ("Could not find the table … in the schema cache"), check that list before reloading the schema cache. Shared types (entities, DTOs) belong in `src/types.ts` and business logic in `src/lib/services/`.

## Tooling and repository conventions

- Pre-commit (husky + lint-staged) runs `eslint --fix` on `*.{ts,tsx,astro}` and `prettier --write` on `*.{json,css,md}`; a lint error blocks the commit.
- Claude Code hooks (`.claude/settings.json`, scripts in `.claude/hooks/`) check the agent's work while it goes. After each Write or Edit, ESLint lints that one file, without `--fix`. At the end of a turn, ESLint lints every changed or new code file, and the whole Vitest suite and `astro check --noSync` run; a failure sends the agent back once (`stop_hook_active`). New untracked files count only in the root, `src/`, `scripts/`, `tests/` and `supabase/`, and a tree that already passed is skipped (`node_modules/.cache/claude-hooks/`). They add to the git hook and CI, and replace neither.
- Prettier uses 120 columns and sorts Tailwind classes; let it reorder them.
- `.nvmrc` pins Node 24.18.0 (npm 11.16.0), and both CI and Workers Builds read it. Change dependencies with that npm. npm 11.6.2 writes lockfiles without the `@emnapi/*` entries that `npm ci` in npm 10.9 and 11.16 requires, so CI fails at install. Local Node below 24.16 prints non-fatal `EBADENGINE` warnings from `eslint-plugin-astro` at install.
- CI (`.github/workflows/ci.yml`) runs on pushes and PRs to `main`: lint, `astro check`, unit tests and build in the `ci` job; the shop gate, watchlist, shop matches and price observations database checks and the smoke test against a local Supabase in the `smoke` job; and the Playwright e2e suite on the production preview, against a local Supabase of its own, in the `e2e` job. It never deploys and needs no repository secrets; keep Cloudflare tokens and Supabase keys out of GitHub.
- `context/` is the 10x workflow surface: `foundation/` living docs are edited in place, `changes/<id>/` holds per-change artefacts created with `/10x-new`, and `archive/` is read-only (see @context/foundation/README.md).
- The 10x CLI (`npx @przeprogramowani/10x-cli@latest`) manages `.claude/`, `.10x-cli.json` and the course block at the bottom of this file, and tracks them by content hash. `.prettierignore` and `.gitattributes` (LF everywhere) keep them byte-identical, so never reformat them. Apply a lesson's course block with `get <lesson> --type rules`: in CLI 1.25.2 a plain `get` removes the block. After any `get` or `sync`, check that the block is still there and re-apply it if not. On Windows the CLI's manifest write sometimes fails with `EPERM` (the file is briefly locked), and some runs print nothing; rerun the same command.

## 10xDevs AI Toolkit - Module 3, Lesson 3 (10xDevs 4.0 Hooks)

Treat a hook as a **quality gate the harness runs for the agent**, not a script you hope the agent notices. Hooks run outside the model, so they survive context compaction and forgotten instructions — but only a hook whose signal actually reaches the agent closes the loop:

```
test-plan.md "Quality Gates" -> pick the moment per gate -> /10x-configure-hook -> prove with sample JSON -> watch the agent fix a deliberate error
```

### Task Router - Where to start

| Skill | Use it when |
| --- | --- |
| `/10x-configure-hook` | Turning the gates from `context/foundation/test-plan.md` into agent hooks, fixing hooks that fire but the agent never reacts to, or auditing an existing hook config. It detects the harness from the repo and carries dated per-harness references. |
| `/10x-test-plan --status` | Read the current gates and rollout state. Changing which gates exist belongs to Lesson 1, not here. |
| `/10x-new` -> `/10x-research` -> `/10x-plan` -> `/10x-implement` | A hook surfaced a failure the agent cannot fix with a trivial correction (wrong business logic, flaky integration). Open a change instead of looping the hook. |

### Hook lifecycle

1. **Trigger** — an event in the harness: a tool finished editing a file, the agent is about to end its turn.
2. **Matcher** — narrows which tool calls or files the hook reacts to. Not every harness honours matchers the same way.
3. **Handler** — usually a shell command or script that reads the event payload as JSON on stdin.
4. **Signal** — what the hook returns. The exit code, stderr, stdout and JSON fields mean different things in different harnesses, and only one channel per event actually reaches the agent. **The signal channel differs per harness — check the skill's references before writing or reviewing a hook.**

A hook that runs but sends its message down the wrong channel is the most common failure: the user sees "hook error", the agent sees nothing and keeps going.

### Moments and layers

The slower the check, the rarer the moment:

| Moment | Typical checks | Reaches the agent? |
| --- | --- | --- |
| Per edit | Lint/format of **the edited file only**; related tests if they are fast | Yes, mid-work |
| End of turn (Stop or its equivalent) | Lint + tests for every file changed this turn, whole-project typecheck | Yes, before the agent hands back |
| Pre-commit (git) | Lint + tests on staged files; catches edits made without the agent | No — blocks the commit |
| Pre-push (git) | Heavier suites, e2e that run locally | No — blocks the push |
| CI | Integration, shared state, infrastructure you do not have locally | No — PR feedback |

Local layers do not replace CI; each one saves a CI round-trip. Start with one per-edit lint hook and one end-of-turn typecheck, then add layers when you see what escapes.

### Contract

- Read the gates from the "Quality Gates" section of `context/foundation/test-plan.md` (by title, not section number). A gate the plan explicitly defers stays deferred unless the user overrides it — quote the deferral when you ask.
- Per-edit hooks check only the file that was edited. Never run `--fix` or a linter over the whole project on every edit.
- End-of-turn hooks that can send the agent back must stop after one retry (the harness's "already continued" flag or equivalent), so an unfixable error does not loop.
- Per-edit hooks only see the harness's edit tools; a file rewritten through a shell command skips them. The end-of-turn hook re-checks every file changed this turn (`git diff`), so it is the net for those edits.
- Timeouts are usually in **seconds**. Check the unit before copying a number.
- Prove every hook before trusting it: run the script with a sample payload on a deliberately broken file and on a clean one, then revert the error.
- Never overwrite existing hook config silently. Audit it, name the defects, merge, and show the diff.

### Lesson boundaries

- Do not change the risk strategy or the gate definitions — that is Lesson 1 (`/10x-test-plan`).
- Do not write new tests here — hooks only run the tests Lesson 2 produced.
- Do not write E2E scenarios or browser verification — that is Lesson 4.
- Do not author CI pipelines or install git-hook managers unasked; recommend pre-commit/pre-push gates, let the user decide.
